| 구분             | Express                | Next.js API Route            |
| -------------- | ---------------------- | ---------------------------- |
| 정체             | 독립적인 Node.js 백엔드 프레임워크 | Next.js에 포함된 API 기능          |
| 전제 조건          | Node.js만 있으면 사용 가능     | 프로젝트가 Next.js여야 자연스러움        |
| 프로젝트 위치        | 보통 `apps/api`처럼 별도 앱   | Next.js 앱 내부 `app/api`       |

| 배포             | 프론트와 백엔드 분리 가능         | 일반적으로 Next.js 앱과 함께 배포       |

| 미들웨어           | Express 생태계 활용 가능      | Next.js 방식에 맞춰 구성            |
| 확장성            | 독립적인 백엔드로 확장하기 편함      | 작은 API는 편하지만 Next.js 의존성이 생김 |
| 현재 WhyMath 적합도 | 높음                     | 현재 구조와 맞지 않음                 |


갱신한 최종 계획을 확인했고 승인합니다.

이제 최종 계획을 기준으로 구현을 시작해줘. 다만 이번에는 전체 단계를 한꺼번에 구현하지 말고 다음 1~4단계까지만 구현해줘.

1. 공유 계약과 검증 스키마
2. `apps/api`의 최소 실행 구조
3. 인증·입력 검증
4. AI Adapter interface와 Fake Adapter 테스트

다음 원칙을 지켜줘.

* 승인된 최종 계획과 파일별 변경 범위를 벗어나지 마.
* 기존 사진 입력, 직접쓰기, Auth, ProtectedRoute, ViewportGuard 기능을 보존해줘.
* 실제 OpenAI·Claude API는 호출하지 마.
* 실제 AI Provider SDK를 설치하거나 연결하지 마.
* Supabase 테이블·Storage·환경변수·배포 설정을 변경하지 마.
* 신규 패키지가 필요하면 설치하지 말고 패키지명, 용도, 대안, 영향을 먼저 보고하고 승인을 기다려줘.
* 각 단계가 끝날 때 관련 typecheck, lint, test, build를 실행해 검증해줘.
* 기존 테스트 실패가 발견되면 원인과 이번 변경과의 관련성을 구분해 보고해줘.
* 구현되지 않은 기능에 가짜 성공 응답을 연결하지 마.
* 광범위한 리팩터링이나 승인되지 않은 구조 변경을 하지 마.
* Git commit은 하지 마.

1~4단계를 완료하면 다음 내용을 통합 보고하고 멈춰줘.

1. 실제 생성·수정한 파일
2. 파일별 변경 내용
3. 구현한 API 계약과 검증 규칙
4. 인증·파일 검증 흐름
5. Fake Adapter의 동작과 테스트 범위
6. 실행한 검증 명령과 결과
7. 남아 있는 오류 또는 주의사항
8. 5단계인 실제 AI Provider 연결 전에 내가 결정하거나 준비해야 할 사항

완료 후에는 5단계로 넘어가지 말고 내 승인을 기다려줘.


다음과 같이 결정하고 승인합니다.

1. ESLint와 TypeScript ESLint

`apps/api`와 `packages/*`에도 TypeScript 정적 검사가 필요하므로 ESLint 적용을 승인합니다. 다만 각 앱과 패키지에 동일한 패키지를 중복 설치하지 말고 다음 원칙을 지켜줘.

* 먼저 워크스페이스 루트와 `apps/web`의 기존 ESLint 패키지, 버전, 설정 파일을 확인해줘.
* 이미 워크스페이스 루트에서 사용할 수 있다면 추가 설치하지 마.
* 설치가 필요하다면 `eslint`와 `typescript-eslint`를 워크스페이스 루트의 공통 `devDependencies`에 한 번만 추가해줘.
* `apps/api`와 각 `packages/*`에 개별적으로 중복 설치하지 마.
* 기존 ESLint 버전을 임의로 업그레이드하거나 설정 방식을 교체하지 마.
* 기존 프로젝트가 `@typescript-eslint/parser`와 `@typescript-eslint/eslint-plugin` 방식을 사용 중이라면, 근거 없이 `typescript-eslint` 통합 패키지 방식으로 마이그레이션하지 마.
* 기존 설정과 호환되는 최소 변경만 수행해줘.
* `apps/web`, `apps/api`, `packages/shared-types`, `packages/validation`을 검사할 수 있도록 공통 설정을 확장해줘.
* TypeScript `strict`와 `any` 금지 원칙을 유지해줘.
* 설치 전 실제로 추가될 패키지와 버전, lockfile 변경 범위를 한 번 확인하고 진행해줘.
* ESLint와 직접 관련 없는 formatter나 플러그인은 추가하지 마.

2. OpenAI 모델

첫 실제 OpenAI Provider 모델은 다음으로 확정합니다.

`AI_MODEL=gpt-5.6-terra`

선정 이유는 이미지 입력, 스트리밍, Structured Outputs를 지원하면서 첫 MVP에서 수학 문제 인식·풀이 품질과 비용의 균형을 검증하기 적합하기 때문입니다.

다음 원칙을 적용해줘.

* OpenAI Responses API를 사용해줘.
* 모델명을 route, service, adapter 코드에 하드코딩하지 마.
* 서버 환경변수 `AI_MODEL`을 통해 모델을 주입해줘.
* `AI_PROVIDER=openai` 설정과 함께 사용해줘.
* OpenAI 고유 응답 타입이 공통 Provider interface나 프론트 API 계약으로 노출되지 않게 해줘.
* 이미지 인식 결과는 Structured Outputs와 기존 검증 스키마를 사용해 검증해줘.
* 풀이 응답의 스트리밍은 기존 계획대로 서버 SSE를 통해 프론트에 전달할 수 있게 해줘.
* recognize와 solve는 분리된 API 및 Adapter 메서드를 유지해줘.
* 이번 단계에서는 recognize와 solve 모두 같은 모델을 사용해 구현을 단순화해줘.
* 모델별 분리 설정은 실제 품질·속도·비용 측정 후 검토해줘.
* `gpt-4o`는 PRD에 남아 있는 예시 모델로 보고 현재 구현 모델로 사용하지 마.
* API Key나 실제 환경변수 값은 코드, 로그, 문서, 테스트 결과에 출력하지 마.

위 결정에 따라 구현을 진행하고, 설치 및 구현 완료 후 다음을 보고해줘.

1. 실제 추가된 패키지와 버전
2. ESLint 설정 및 검사 대상
3. 변경된 workspace 파일과 lockfile
4. OpenAI Adapter에서 사용한 Responses API 구조
5. 이미지 입력·Structured Outputs·스트리밍 처리 방식
6. 실행한 lint, typecheck, test, build 결과
7. 실제 Provider 연결 과정에서 남은 오류나 주의사항


보고 내용을 확인했습니다. 전체 구조는 승인하지만, 바로 6단계로 넘어가지 말고 먼저 5단계의 실제 Provider 검증을 완료해줘.

다음 사항을 보완해줘.

1. `.env.example`은 다음과 같이 비밀이 아닌 설정값을 명시해줘.

```env
AI_PROVIDER=openai
AI_MODEL=gpt-5.6-terra
OPENAI_API_KEY=
```

* 실제 API Key는 `.env.example`, 코드, 문서, 테스트 fixture에 넣지 마.
* 실제 `.env`가 Git 추적 대상에서 제외되는지 확인해줘.
* `AI_PROVIDER`, `AI_MODEL`, `OPENAI_API_KEY`가 없거나 비어 있을 때 서버 시작 또는 Provider 초기화 단계에서 원인을 알 수 있는 명확한 설정 오류를 반환해줘.
* 코드 내부의 임의 기본 모델로 조용히 fallback하지 마.

2. 일반 자동 테스트와 실제 API 라이브 테스트를 분리해줘.

* 기존 mock 기반 테스트는 그대로 유지한다.
* 일반 `test` 명령에서는 실제 API를 절대 호출하지 않는다.
* 라이브 테스트는 별도 명령이나 명시적 플래그가 있을 때만 실행되게 한다.
* API Key가 없으면 라이브 테스트를 실행하지 말고 명확히 skip한다.
* CI에서는 기본적으로 라이브 테스트를 실행하지 않는다.
* 라이브 테스트가 자동으로 반복 실행되거나 예상하지 못한 비용을 발생시키지 않게 한다.

3. 내가 로컬 `.env`에 API Key를 직접 설정한 뒤, 다음 최소 라이브 스모크 테스트를 실행할 수 있게 안내해줘.

* 실제 수학 문제 이미지 1장으로 `recognizeProblem` 호출
* 응답이 기존 Structured Outputs 검증 스키마를 통과하는지 확인
* 인식된 문제로 `solve` 호출
* SSE 스트리밍의 시작, 데이터 수신, 정상 종료 확인
* 잘못된 이미지, Provider 오류, timeout 중 최소 한 가지 오류 흐름 확인
* API Key, Authorization 헤더, 원본 이미지, base64 데이터가 로그에 출력되지 않는지 확인

실제 키나 `.env`의 내용을 출력하거나 Git에 커밋하지 마.

4. in-memory Map은 6단계 프론트 연결 검증까지 임시로 유지해도 된다.

다만 다음을 지켜줘.

* 영구 저장소처럼 취급하지 않는다.
* 서버 재시작 시 데이터가 소실된다는 점을 문서에 명시한다.
* 7단계 Supabase 저장을 쉽게 연결할 수 있도록 저장 책임을 route 내부에 직접 고정하지 말고 repository 또는 동등한 추상화 뒤에 둔다.
* 7단계 완료 전에는 운영용 영구 저장이 구현된 것처럼 표시하지 않는다.

5. Claude Adapter 스텁은 이번 OpenAI vertical slice 동안 유지해도 된다. 호출 시 명확한 미구현 오류를 반환하고, OpenAI 전용 타입이 공통 `LLMAdapter` interface에 노출되지 않게 해줘.

위 보완과 라이브 스모크 테스트가 성공하면 5단계를 완료로 보고해줘. 보고에는 다음을 포함해줘.

1. 변경 파일
2. 환경변수 검증 방식
3. 라이브 테스트 실행 방법
4. 실제 recognize 결과의 스키마 검증 여부
5. solve SSE 스트리밍 검증 결과
6. 오류 처리 검증 결과
7. 민감정보 로그 노출 여부
8. 사용한 Provider와 실제 모델명
9. 비용이 발생한 실제 API 호출 횟수

5단계 검증이 성공하면 멈추지 말고, 승인된 기존 최종 계획 범위 안에서 6단계인 프론트 문제 제출 연결을 진행해줘. 7단계 Supabase 저장은 6단계 완료 보고 후 별도 승인을 기다려줘.
