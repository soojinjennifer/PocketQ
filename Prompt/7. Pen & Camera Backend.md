[사용 에이전트: plan-agent]

`plan-agent`를 사용해 현재 `/solve`의 사진·직접쓰기 입력 구조와 프론트엔드 영향 범위를 분석하고, 백엔드·API·Supabase·AI Adapter 영역은 메인 에이전트가 직접 분석해줘.

두 분석 결과를 분리하지 말고 하나의 통합 구현 계획으로 정리해줘.

이번 단계에서는 `development-agent`를 사용하거나 코드를 수정하지 마.

## 목표

사진 촬영과 직접쓰기 입력을 공통 문제 입력으로 변환하여 다음 흐름으로 연결하기 위한 구현 계획을 수립한다.

`/solve 문제 입력 → 풀이 옵션 선택 → 문제 제출 → 백엔드 검증 → AI 풀이 요청 → 구조화된 풀이 응답 반환`

이번 단계는 실제 AI 풀이 기능의 첫 번째 vertical slice를 설계하는 단계다.

## 현재 완료된 기능

다음 기능은 구현이 완료된 것으로 전제하되, 반드시 현재 코드에서 실제 상태를 확인해줘.

* `/solve → /camera → /camera/preview → /solve` 사진 입력 흐름
* 촬영 이미지의 라우터 state 전달
* 촬영 사진 표시 및 재촬영
* 직접쓰기 필기 캔버스
* Apple Pencil·터치·마우스 입력
* Pen Rail 도구 동작
* 사진 또는 유효한 필기가 없을 때 `풀기` 버튼 비활성화
* 풀이 옵션 체크박스
* 기존 Auth, ProtectedRoute, ViewportGuard
* 기존 typecheck, lint, test, build 통과

완료된 기능을 다시 구현하거나 임의로 리팩터링하지 마.

## 분석 범위

### 1. 공통 문제 입력 모델

사진과 직접쓰기를 백엔드가 처리할 수 있는 공통 입력으로 만드는 방법을 분석해줘.

다음을 포함한다.

* 사진 입력의 현재 데이터 형식
* 필기 입력의 현재 데이터 형식
* 필기 획 데이터를 이미지로 변환할 필요가 있는지
* 사진과 필기를 모두 `File` 또는 `Blob`으로 통일할지
* 원본 획 데이터도 함께 전달할지
* object URL을 API 데이터로 사용할 수 없는 점의 처리
* 이미지 MIME type과 최대 크기
* 이미지 압축·리사이즈 필요 여부
* iPad에서 생성되는 이미지 형식 호환성
* 선택한 풀이 옵션 전달 구조
* 요청 중 입력 모드 전환이나 라우트 이동 처리

PRD 근거 없이 사진과 필기 데이터를 동시에 보내도록 결정하지 마.

### 2. API 계약

PRD를 기준으로 첫 번째 풀이 요청 API의 정확한 계약을 제안해줘.

최소한 다음을 검토한다.

* endpoint와 HTTP method
* 인증 필요 여부
* `multipart/form-data`와 JSON 중 적합한 방식
* 문제 이미지
* 입력 출처(`camera` 또는 `handwriting`)
* 선택한 풀이 옵션
* 학년 정보
* 사용자 식별 방식
* 요청 ID 또는 idempotency key 필요 여부
* 성공 응답
* 입력 검증 오류
* 인증 오류
* 이미지 분석 실패
* AI Provider 오류
* timeout
* rate limit
* 서버 내부 오류

프론트와 백엔드가 공유할 TypeScript 계약을 어디에 둘지도 제안해줘.

가능하면 응답은 자유 텍스트 하나가 아니라 다음 단계의 결과 화면에서 안전하게 사용할 수 있는 구조화된 타입으로 설계해줘.

단, 필드명과 구조는 `docs/PRD_WHYMATH.md`의 결과 요구사항을 먼저 확인해 결정한다.

### 3. 동기·비동기 처리 방식

이미지 분석과 AI 풀이 시간이 길어질 수 있으므로 다음 방식을 비교해줘.

* 단일 동기 요청
* 제출 후 polling
* 비동기 job 구조
* streaming 응답

현재 배포 환경, MVP 범위, 예상 timeout, 구현 복잡도를 비교하고 이번 단계에 적합한 방식을 하나 추천해줘.

근거 없이 Redis, Queue, WebSocket 같은 인프라를 추가하지 마.

### 4. AI Adapter 구조

특정 AI SDK를 feature나 route에 직접 결합하지 않는 Adapter 구조를 계획해줘.

다음을 포함한다.

* Provider interface
* 요청 정규화
* 이미지와 프롬프트 전달
* 구조화된 응답 파싱
* 스키마 검증
* Provider 오류 변환
* timeout과 재시도 정책
* 모델명과 환경변수 관리
* 테스트용 fake adapter
* 실제 Provider 교체 가능성
* 프롬프트 파일의 위치와 버전 관리
* 사용자 입력이 시스템 지시를 덮어쓰지 못하도록 하는 경계

현재 단계에서는 특정 Provider나 모델을 임의로 확정하지 말고, PRD·기존 코드·환경변수에서 확인되지 않으면 사용자 결정 사항으로 남겨줘.

### 5. Supabase 데이터 구조

풀이 요청과 결과를 저장해야 하는지 PRD를 먼저 확인해줘.

저장이 필요하다면 최소한 다음을 검토한다.

* 사용자 문제 제출
* 입력 방식
* 이미지 Storage 경로
* 처리 상태
* 선택한 풀이 옵션
* 인식된 문제
* 풀이 결과
* 오류 정보
* 생성·수정 시각
* 사용자 소유권
* RLS
* 삭제 정책
* 마이페이지 풀이 이력과의 연결 가능성

민감한 원본 이미지와 전체 AI 로그를 무조건 저장하도록 계획하지 마.

이번 첫 vertical slice에서 필요한 필드와 향후 단계에서 추가할 필드를 구분해줘.

### 6. 보안과 운영

다음 항목을 계획에 포함해줘.

* AI API Key를 프론트에 노출하지 않기
* Supabase access token 검증
* MIME type·파일 크기·이미지 해상도 검증
* CORS
* 요청 횟수 제한
* 사용자별 데이터 접근 통제
* 로그에서 이미지·토큰·개인정보 제외
* AI 응답 검증
* 중복 제출 방지
* 서버 timeout
* 개발·테스트·운영 환경변수 분리

실제 환경변수 값이나 비밀키를 출력하지 마.

## 구조 원칙

* `pages`는 기능을 조립하고 API 로직을 직접 갖지 않는다.
* 프론트의 문제 제출 로직은 적절한 `features` 영역에 둔다.
* 공유 API 타입은 기존 `packages/contracts`, `shared-types`, `validation`의 책임을 확인한 후 배치한다.
* 백엔드 route에 Provider별 구현을 직접 작성하지 않는다.
* AI Provider SDK를 프론트에 설치하지 않는다.
* TypeScript strict를 유지하고 `any`를 사용하지 않는다.
* 기존 사진·직접쓰기 기능을 보존한다.
* 기존 Auth와 라우팅을 보존한다.
* 신규 패키지는 기존 의존성으로 구현할 수 없는 경우에만 제안한다.
* 패키지 설치가 필요하면 패키지명·용도·대안·영향을 보고하고 승인을 기다린다.
* 문서에 없는 과도한 Clean Architecture 계층을 만들지 않는다.
* 구현되지 않은 API를 연결한 것처럼 보이게 하는 가짜 성공 응답을 만들지 않는다.
