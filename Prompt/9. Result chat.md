WhyMath의 6단계 결과 화면 구현 이후, 아직 구현되지 않은 후속 질문 Footer를 `6.5단계 — 후속 질문 Footer 및 Chat 연결`로 진행하려고 합니다.

현재 다음 기능은 완료되어 있습니다.

* ResultPanel Header / Body
* ResultCard Concept / Steps
* AnswerBox
* RecognizedProblemBar
* 공통 Badge
* KaTeX 수식 렌더링
* 실제 문제 인식 및 최초 풀이 결과 연결
* 기존 Spinner 기반 로딩·인식 중·풀이 중 상태

다음 기능은 아직 구현되지 않았습니다.

* ResultPanel Footer
* 추천 질문 및 주제 pill
* 후속 질문 입력창
* 전송 버튼
* 후속 질문과 답변 표시
* 후속 질문 API 연결
* 대화 상태 관리

7단계 Supabase 영구 저장으로 넘어가기 전에 6.5단계에서 후속 질문의 UI, 상태 모델, API 계약을 확정해야 합니다.

## 0. PRD 보완안 검토

현재 `docs/PRD_WHYMATH.md`의 4.5 후속 질문 대화에는 `CHAT-1~4`만 정의되어 있습니다.

다음 보완 방향을 기준으로 검토해줘.

* CHAT-1: 동일 문제, 최초 풀이, 이전 대화 맥락 유지
* CHAT-2: 키보드 텍스트 입력과 제출 기준
* CHAT-3: 질문에 직접 답하면서 개념과 이유를 설명하도록 수정
* CHAT-4: 대화 저장과 마이페이지 재열람은 P1 유지
* CHAT-5: ResultPanel Footer 도킹과 Body 스크롤
* CHAT-6: 추천 질문 pill 선택 시 입력창에 문구를 채우되 자동 전송하지 않음
* CHAT-7: 빈 질문·공백 질문·중복 전송 방지
* CHAT-8: 기존 Spinner, 완료 응답 표시, 오류·재시도. 실시간 스트리밍 표시는 P1로 분리
* CHAT-9: 새 문제 시작 시 현재 대화 초기화
* CHAT-10: Apple Pencil 질문 입력을 별도의 P2 요구사항으로 분리

이번 응답에서는 PRD 파일을 바로 수정하지 말고 다음을 보고해줘.

1. 기존 CHAT-1~4와 보완안의 충돌 여부
2. 기존 PRD의 다른 요구사항과 중복되는 항목
3. 요구사항 ID와 우선순위의 적절성
4. 실제 코드가 이미 지원하는 항목과 새로 구현해야 할 항목
5. 최종적으로 PRD 4.5에 반영할 수정안

## 1. plan-agent 호출

`plan-agent`를 실제 호출하여 현재 코드와 후속 질문 백엔드를 분석해줘.

`plan-agent`는 Read, Grep, Glob만 사용하고 코드를 수정하면 안 됩니다.

다음 자료를 확인해줘.

* `docs/PRD_WHYMATH.md`
* `FIGMA_SCREEN_MAP.md`
* ResultPanel 및 결과 화면 컴포넌트
* 현재 문제·풀이 상태를 관리하는 hook, store 또는 page state
* 프론트엔드 API client
* `packages/contracts`
* `packages/shared-types`
* `packages/validation`
* `apps/api`의 route, controller, service
* LLMAdapter
* FakeAdapter
* OpenAIAdapter
* `chat(req)` 관련 선언과 구현
* 후속 질문 관련 테스트
* 대화 저장 관련 타입이나 스키마

다음 구현 단계를 반드시 구분해 보고해줘.

* 타입 또는 인터페이스 선언만 존재
* FakeAdapter만 구현
* OpenAIAdapter에 실제 `chat()` 구현 존재
* API route와 controller 존재
* 프론트 API client 존재
* 프론트부터 OpenAI까지 실제 호출 가능
* Supabase 영구 저장까지 구현

이름이나 메서드만 존재하는 것을 기능 구현 완료로 판단하지 마.

다음 내용도 분석해줘.

1. 후속 질문 API endpoint
2. 요청·응답 계약
3. 일반 완료 응답인지 스트리밍 응답인지
4. 인식된 문제와 최초 풀이를 전달하는 방식
5. 이전 질문·답변을 전달하는 방식
6. 인증 및 입력 검증
7. 빈 질문과 최대 입력 길이 검증
8. 중복 요청 방지와 요청 취소 처리
9. 새 문제 시작 시 대화 초기화 위치
10. Supabase 없이 현재 화면 상태만으로 멀티턴 대화를 유지할 수 있는지
11. 7단계 저장에 필요한 문제·풀이·대화 식별자
12. 기존 테스트와 누락된 테스트

## 2. design-agent 호출

`plan-agent` 분석이 끝나면 `design-agent`를 실제 호출하여 최신 Figma와 첨부된 Footer 이미지를 분석해줘.

다음 요소를 확인해줘.

1. Footer의 정확한 Figma frame/node
2. ResultPanel Header / Body / Footer 구조
3. Body 스크롤과 Footer 도킹 방식
4. 추천 질문 pill의 크기, 간격, 색상, border, radius
5. 기존 Badge variant 재사용 가능 여부
6. 입력창의 크기, padding, placeholder, focus 상태
7. 전송 버튼의 크기, 색상, 아이콘, 활성·비활성 상태
8. iPad 키보드가 열렸을 때 Footer 배치
9. iPad 세로·가로 및 Split View 대응
10. 질문·답변이 추가되는 대화 영역
11. 긴 대화의 스크롤 방식
12. 상단 추천 질문 버튼과 하단 주제 pill의 차이
13. 로딩·완료·오류 상태 프레임 존재 여부

Figma에 없는 상태나 대화 화면을 임의로 설계하지 마. 확인할 수 없다면 필요한 frame/node와 결정이 필요한 내용을 보고해줘.

추천 pill은 다음 동작을 기본안으로 검토해줘.

```text
pill 선택
→ 문제 맥락에 맞는 질문 문구를 입력창에 채움
→ 입력창 focus
→ 사용자가 확인 또는 수정
→ 전송 버튼이나 Enter로 제출
```

자동 전송은 하지 않는다.

## 3. 통합 구현 계획

두 에이전트의 결과를 다음 형식으로 통합해줘.

### A. PRD 수정 계획

* 변경할 요구사항
* 추가할 요구사항
* 우선순위
* 수용 기준
* 기존 요구사항과의 관계

### B. 실제 백엔드 구현 상태

| 구분 | 존재 여부 | 관련 파일 | 실제 동작 여부 | 추가 작업 |
| -- | ----- | ----- | -------- | ----- |

### C. Figma와 컴포넌트 매핑

| Figma 영역 | 기존 컴포넌트 | 신규 여부 | 처리 방식 | 관련 파일 |
| -------- | ------- | ----- | ----- | ----- |

다음 후보를 검토하되 기존 컴포넌트로 해결할 수 있으면 중복 생성하지 마.

* `ResultPanelFooter`
* `SuggestionChip`
* `ChatInput`
* `SendButton`
* `ChatMessage` 또는 기존 `ChatBubble`

### D. 상태 모델

다음 상태와 전환 조건을 정의해줘.

* `idle`
* `typing`
* `submitting`
* `success`
* `error`
* `retrying`

다음 동작도 포함해줘.

* 빈 입력과 공백 입력 차단
* 전송 중 중복 제출 방지
* 전송 버튼과 Enter 제출
* 성공 후 입력값 초기화
* 실패 시 입력값 유지
* 재시도
* 추천 pill 선택
* 대화 추가 후 스크롤
* 새 문제 시작 시 대화 초기화

### E. 구현 분기

#### 실제 후속 질문 API가 있는 경우

* 기존 계약을 보존하여 Footer와 연결
* 가짜 응답 없이 실제 데이터를 사용
* Supabase 저장은 이번 단계에서 제외

#### Adapter만 있고 API endpoint가 없는 경우

* 필요한 API route, validation, contract, client 작업을 별도 범위로 제시
* 승인 없이 백엔드를 구현하지 않음

#### 인터페이스 또는 스텁만 있는 경우

* 프론트 UI와 백엔드 구현을 `6.5A`와 `6.5B`로 분리
* 실제 연결이 불가능한 이유와 필요한 작업을 보고
* 가짜 성공 응답을 만들지 않음

#### Figma에 후속 답변 화면이 없는 경우

* 확정된 Footer UI와 입력 상태까지만 계획
* ChatMessage 화면을 임의로 설계하지 않음
* 필요한 Figma frame/node를 보고

### F. 파일별 변경 계획

각 파일에 대해 다음을 작성해줘.

* 파일 경로
* 기존 역할
* 변경 내용
* 변경 이유
* 신규 또는 수정
* 테스트
* 회귀 위험

## 구현 원칙

* 이번 응답에서는 PRD와 코드를 수정하지 않는다.
* 분석과 최종 계획을 보여준 뒤 승인을 기다린다.
* 기존 문제 인식과 최초 풀이 기능을 보존한다.
* ResultPanel, ResultCard, AnswerBox, RecognizedProblemBar를 보존한다.
* 기존 Spinner를 유지한다.
* 이번 단계에서 실시간 스트리밍 표시를 구현하지 않는다.
* KaTeX 적용 범위를 확대하지 않는다.
* 기존 API 계약을 승인 없이 변경하지 않는다.
* 가짜 후속 질문 응답을 만들지 않는다.
* Supabase 테이블, Storage, RLS를 변경하지 않는다.
* CHAT-4 영구 저장은 7단계 범위로 유지한다.
* Figma에 없는 UI를 임의로 추가하지 않는다.
* 기존 디자인 토큰과 공통 컴포넌트를 우선 재사용한다.
* 사진과 직접쓰기에서 동일한 Footer를 사용한다.
* Auth, ProtectedRoute, ViewportGuard를 변경하지 않는다.
* 환경변수와 API Key를 출력하거나 변경하지 않는다.
* 광범위한 리팩터링을 하지 않는다.
* Git commit을 하지 않는다.

## 6.5단계 완료 조건

* 보완된 CHAT 요구사항이 승인 후 PRD에 반영된다.
* Figma와 동일한 Footer가 ResultPanel 하단에 표시된다.
* 풀이와 대화 영역은 스크롤되고 Footer는 하단에 유지된다.
* 추천 pill은 입력창을 채우고 자동 전송하지 않는다.
* 빈 질문과 중복 제출이 차단된다.
* 실제 API가 있으면 실제 후속 질문과 답변이 연결된다.
* 질문에는 현재 문제, 최초 풀이, 이전 대화 맥락이 유지된다.
* 실패 시 입력값이 유지되고 재시도할 수 있다.
* 새 문제 시작 시 현재 대화가 초기화된다.
* 사진과 직접쓰기 모두 같은 Footer를 사용한다.
* iPad 키보드와 Split View에서 입력창이 가려지지 않는다.
* typecheck, lint, test, build가 통과한다.
* 기존 문제 인식과 최초 풀이에 회귀가 없다.

분석, PRD 최종 수정안, 통합 구현 계획을 보여준 뒤 코드와 문서를 수정하지 말고 내 승인을 기다려줘.
