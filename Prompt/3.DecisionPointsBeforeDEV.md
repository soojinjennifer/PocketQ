구현 전 결정사항을 다음과 같이 확정한다.

가장 먼저 `docs/FIGMA_SCREEN_MAP.md`를 읽어라.

이 문서를 Figma 화면명과 프론트엔드 라우트명의
최우선 기준이자 단일 기준 문서로 사용한다.

PRD, PROJECT_STRUCTURE.md 또는 기존 코드의 명칭이
FIGMA_SCREEN_MAP.md와 다르면 임의로 하나를 선택하지 말고,
FIGMA_SCREEN_MAP.md를 기준으로 수정 대상을 보고해라.

아직 코드를 수정하거나 패키지를 설치하지 마라.
먼저 관련 문서에 반영할 변경 계획만 보고하고 내 승인을 기다려라.

[1. 지원 화면 환경]

v1은 1194×834 기준의 iPad 가로 전체 화면만 공식 지원한다.

- 세로 화면용 레이아웃은 별도로 구현하지 않는다.
- 기기가 세로 방향이면 “기기를 가로로 돌려주세요” 안내 화면을 표시한다.
- Split View 등 최소 지원 너비 미만이면
  “전체 화면에서 이용해 주세요” 안내 화면을 표시한다.
- 일반 웹 브라우저에서 화면 방향을 강제로 고정할 수 있다고 가정하지 않는다.
- 설치형 PWA 환경에서 가능한 경우에만 landscape orientation을 보조 적용한다.
- 세로·가로 안내 화면은 서비스 라우트가 아닌 전역 환경 가드로 처리한다.

[2. 프로젝트 구조]

v1은 `apps/web` 단일 앱 중심으로 구현한다.

- Turborepo와 Nx는 도입하지 않는다.
- 기존 pnpm workspace만 유지한다.
- 빈 `packages/ui`, `packages/shared-types`,
  `packages/validation`은 현재 사용하지 않는다.
- 프론트엔드와 다른 앱 또는 백엔드가 실제로 타입을 공유하게 될 때만
  `packages/contracts` 도입을 검토한다.

[3. 공통 코드의 위치]

현재 디자인 토큰과 공통 UI는 다음 위치에서 관리한다.

- 디자인 토큰과 공통 스타일: `apps/web/src/shared/styles`
- 공통 UI 컴포넌트: `apps/web/src/shared/ui`
- 특정 기능 전용 컴포넌트: `apps/web/src/features`
- 페이지 조립 코드: `apps/web/src/pages`

`packages/*`에는 둘 이상의 앱이 실제로 공유하는 코드만 둔다.

[4. 화면명과 라우트명]

화면명은 `docs/FIGMA_SCREEN_MAP.md`에 기록된
Figma 프레임명을 그대로 사용한다.

다음 매핑을 기준으로 문서와 코드를 통일한다.

1. 로그인
   - Figma 프레임: `1. Login/Desktop`
   - 라우트: `/login`

2. 학년 선택
   - Figma 프레임: `2. Grade Setup`
   - 라우트: `/grade-setup`

3. 문제 풀기
   - Figma 프레임: `3 · Solve/Landscape`
   - 라우트: `/solve`

4. 마이페이지
   - Figma 프레임: `4 · MyPage`
   - 라우트: `/mypage`

5. 문제 촬영
   - Figma 프레임: `5 · Capture.Camera`
   - 라우트: `/camera`

6. 촬영 결과 미리보기
   - Figma 프레임: `6 · preview.Camera`
   - 라우트: `/camera/preview`

다음과 같은 대체 명칭은 이번 단계에서 사용하지 않는다.

- `/auth`
- `/onboarding`
- `/onboarding/grade`
- `/solve/camera`
- `/solve/camera/review`
- `/camera/review`

`/mypage/history`와 `/mypage/profile`은 현재
FIGMA_SCREEN_MAP.md에 독립 화면으로 정의되어 있지 않으므로
이번 단계에서 별도 라우트로 만들지 않는다.

마이페이지 세부 화면이 Figma와 화면 맵에 추가된 이후에
중첩 라우트 분리를 다시 검토한다.

[5. 카메라 라우트 구조]

카메라 촬영과 미리보기는 하나의 기능 흐름이지만,
브라우저 탐색과 화면 책임을 분명하게 하기 위해
다음 중첩 라우트로 구현한다.

- 촬영 화면: `/camera`
- 미리보기 화면: `/camera/preview`

동작 규칙은 다음과 같다.

1. `/camera`에서 촬영을 완료하면 `/camera/preview`로 이동한다.
2. 미리보기 화면에서 “다시 촬영”을 선택하면 `/camera`로 돌아간다.
3. 촬영 데이터 없이 `/camera/preview`에 직접 접근하면
   `/camera`로 이동시킨다.
4. 촬영 데이터는 라우트 URL이나 전역 공통 UI에 저장하지 않는다.
5. 카메라 세션과 촬영 이미지 상태는 `features/camera`에서 관리한다.
6. 새로고침으로 임시 촬영 데이터가 사라진 경우 `/camera`로 복귀시킨다.
7. Figma 프레임명은 변경하지 않고 코드의 페이지명만
   의미가 분명하게 정한다.

권장 코드명은 다음과 같다.

- `CameraCapturePage`
- `CameraPreviewPage`

[6. Tailwind CSS 4]

- Vite 연결에는 기존 설정을 확인한 뒤 `@tailwindcss/vite`를 사용한다.
- 디자인 토큰 연결에는 CSS-first `@theme` 방식을 사용한다.
- 기존에 정상 작동하는 설정은 불필요하게 교체하지 않는다.

권장 구조:

apps/web/src/shared/styles/
- tokens.css
- theme.css
- global.css

[7. Radius와 Spacing]

Figma Variable이 없으므로 임의의 스케일을 만들지 않는다.

다음 순서로 처리한다.

1. Figma 컴포넌트와 프레임의 raw 값을 실측한다.
2. 반복되는 값을 식별한다.
3. `Figma 실측값 / 제안 토큰명 / 사용 화면·컴포넌트` 표를 작성한다.
4. 내가 승인한 값만 디자인 토큰으로 구현한다.

[8. 다크모드]

v1에서는 다크모드를 지원하지 않는다.

- `dark:` Variant를 사용하지 않는다.
- 다크모드 전용 토큰을 만들지 않는다.
- 시스템 다크모드를 자동 적용하지 않는다.
- 전역 스타일에는 `color-scheme: light`를 적용한다.

[9. 기능 컴포넌트]

`ChatBubble`, `MathActivityCard`, `HistoryRow`는
하나의 컴포넌트로 통합하지 않는다.

- 공통 외형은 `shared/ui`의 `Card` 또는 `Surface`를 재사용한다.
- 기능별 컴포넌트는 해당 feature 내부에 둔다.
- `ChatBubble`과 `MathActivityCard`는 현재 확인된 6개 Figma 프레임에서
  실제 인스턴스가 확인되지 않았으므로 최종 Variant 구현을 보류한다.
- `HistoryRow` 역시 독립된 마이페이지 상세 화면이 확정되기 전에는
  구현 범위를 확장하지 않는다.

[10. 신규 npm 의존성]

새 직접 의존성이 필요하면 설치 전에 다음을 표로 보고한다.

- 패키지명
- 정확한 버전
- 사용 목적
- 기존 구성으로 대체 가능한지
- 필수 또는 선택 여부

내가 직접 의존성 목록을 일괄 승인한 뒤 설치한다.
승인 후 새로운 직접 의존성이 추가로 필요하면 다시 승인을 요청한다.
