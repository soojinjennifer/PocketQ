다음 순서는 사진·필기 입력을 실제 AI 풀이로 연결하기 위한 백엔드/API 구조 설계입니다.

기존 plan-agent는 프론트엔드 설계 중심이므로, 프론트 입력 구조와 영향 범위는 plan-agent가 분석하고 백엔드·DB·AI Adapter는 메인 Claude가 분석하게 하는 것이 안전합니다. 아직 실제 API나 DB는 구현하지 않습니다.

[사용 에이전트: plan-agent]

plan-agent를 사용해 현재 /solve의 사진·직접쓰기 입력 구조와 프론트엔드 영향 범위를 분석하고, 백엔드·API·Supabase·AI Adapter 영역은 메인 에이전트가 직접 분석해줘.

두 분석 결과를 분리하지 말고 하나의 통합 구현 계획으로 정리해줘.

이번 단계에서는 development-agent를 사용하거나 코드를 수정하지 마.

목표

사진 촬영과 직접쓰기 입력을 공통 문제 입력으로 변환하여 다음 흐름으로 연결하기 위한 구현 계획을 수립한다.

/solve 문제 입력 → 풀이 옵션 선택 → 문제 제출 → 백엔드 검증 → AI 풀이 요청 → 구조화된 풀이 응답 반환

이번 단계는 실제 AI 풀이 기능의 첫 번째 vertical slice를 설계하는 단계다.

현재 완료된 기능

다음 기능은 구현이 완료된 것으로 전제하되, 반드시 현재 코드에서 실제 상태를 확인해줘.

  • /solve → /camera → /camera/preview → /solve 사진 입력 흐름

  • 촬영 이미지의 라우터 state 전달

  • Pen Rail 도구 동작

  • 사진 또는 유효한 필기가 없을 때 풀기 버튼 비활성화

  • 풀이 옵션 체크박스

  • 기존 Auth, ProtectedRoute, ViewportGuard

  • 기존 typecheck, lint, test, build 통과

완료된 기능을 다시 구현하거나 임의로 리팩터링하지 마.

분석 범위

1. 공통 문제 입력 모델

사진과 직접쓰기를 백엔드가 처리할 수 있는 공통 입력으로 만드는 방법을 분석해줘.

다음을 포함한다.

  • 사진 입력의 현재 데이터 형식

  • 필기 입력의 현재 데이터 형식

  • 필기 획 데이터를 이미지로 변환할 필요가 있는지

  • 사진과 필기를 모두 File 또는 Blob으로 통일할지

  • 원본 획 데이터도 함께 전달할지

  • object URL을 API 데이터로 사용할 수 없는 점의 처리

  • 이미지 MIME type과 최대 크기

  • 이미지 압축·리사이즈 필요 여부

  • iPad에서 생성되는 이미지 형식 호환성

  • 선택한 풀이 옵션 전달 구조

  • 요청 중 입력 모드 전환이나 라우트 이동 처리

PRD 근거 없이 사진과 필기 데이터를 동시에 보내도록 결정하지 마.

2. API 계약

PRD를 기준으로 첫 번째 풀이 요청 API의 정확한 계약을 제안해줘.

최소한 다음을 검토한다.

  • endpoint와 HTTP method

  • 인증 필요 여부

  • multipart/form-data와 JSON 중 적합한 방식

  • 문제 이미지

  • 입력 출처(camera 또는 handwriting)

  • 선택한 풀이 옵션

  • 학년 정보

  • 사용자 식별 방식

  • 요청 ID 또는 idempotency key 필요 여부

  • 성공 응답

  • 입력 검증 오류

  • 인증 오류

  • 이미지 분석 실패

  • AI Provider 오류

  • timeout

  • rate limit

  • 서버 내부 오류

프론트와 백엔드가 공유할 TypeScript 계약을 어디에 둘지도 제안해줘.

가능하면 응답은 자유 텍스트 하나가 아니라 다음 단계의 결과 화면에서 안전하게 사용할 수 있는 구조화된 타입으로 설계해줘.

단, 필드명과 구조는 docs/PRD_WHYMATH.md의 결과 요구사항을 먼저 확인해 결정한다.

3. 동기·비동기 처리 방식

이미지 분석과 AI 풀이 시간이 길어질 수 있으므로 다음 방식을 비교해줘.

  • 단일 동기 요청

  • 제출 후 polling

  • 비동기 job 구조

  • streaming 응답

현재 배포 환경, MVP 범위, 예상 timeout, 구현 복잡도를 비교하고 이번 단계에 적합한 방식을 하나 추천해줘.

근거 없이 Redis, Queue, WebSocket 같은 인프라를 추가하지 마.

4. AI Adapter 구조

특정 AI SDK를 feature나 route에 직접 결합하지 않는 Adapter 구조를 계획해줘.

다음을 포함한다.

  • Provider interface

  • 요청 정규화

  • 이미지와 프롬프트 전달

  • 구조화된 응답 파싱

  • 스키마 검증

  • Provider 오류 변환

  • timeout과 재시도 정책

  • 모델명과 환경변수 관리

  • 테스트용 fake adapter

  • 실제 Provider 교체 가능성

  • 프롬프트 파일의 위치와 버전 관리

  • 사용자 입력이 시스템 지시를 덮어쓰지 못하도록 하는 경계

현재 단계에서는 특정 Provider나 모델을 임의로 확정하지 말고, PRD·기존 코드·환경변수에서 확인되지 않으면 사용자 결정 사항으로 남겨줘.

5. Supabase 데이터 구조

풀이 요청과 결과를 저장해야 하는지 PRD를 먼저 확인해줘.

저장이 필요하다면 최소한 다음을 검토한다.

  • 사용자 문제 제출

  • 입력 방식

  • 이미지 Storage 경로

  • 처리 상태

  • 선택한 풀이 옵션

  • 인식된 문제

  • 풀이 결과

  • 오류 정보

  • 생성·수정 시각

  • 사용자 소유권

  • RLS

  • 삭제 정책

  • 마이페이지 풀이 이력과의 연결 가능성

민감한 원본 이미지와 전체 AI 로그를 무조건 저장하도록 계획하지 마.

이번 첫 vertical slice에서 필요한 필드와 향후 단계에서 추가할 필드를 구분해줘.

6. 보안과 운영

다음 항목을 계획에 포함해줘.

  • AI API Key를 프론트에 노출하지 않기

  • Supabase access token 검증

  • MIME type·파일 크기·이미지 해상도 검증

  • CORS

  • 요청 횟수 제한

  • 사용자별 데이터 접근 통제

  • 로그에서 이미지·토큰·개인정보 제외

  • AI 응답 검증

  • 중복 제출 방지

  • 서버 timeout

  • 개발·테스트·운영 환경변수 분리

실제 환경변수 값이나 비밀키를 출력하지 마.

구조 원칙

  • pages는 기능을 조립하고 API 로직을 직접 갖지 않는다.

  • 프론트의 문제 제출 로직은 적절한 features 영역에 둔다.

  • 공유 API 타입은 기존 packages/contracts, shared-types, validation의 책임을 확인한 후 배치한다.

  • 백엔드 route에 Provider별 구현을 직접 작성하지 않는다.

  • AI Provider SDK를 프론트에 설치하지 않는다.

  • TypeScript strict를 유지하고 any를 사용하지 않는다.

  • 기존 사진·직접쓰기 기능을 보존한다.

  • 기존 Auth와 라우팅을 보존한다.

  • 신규 패키지는 기존 의존성으로 구현할 수 없는 경우에만 제안한다.

  • 패키지 설치가 필요하면 패키지명·용도·대안·영향을 보고하고 승인을 기다린다.

  • 문서에 없는 과도한 Clean Architecture 계층을 만들지 않는다.

  • 구현되지 않은 API를 연결한 것처럼 보이게 하는 가짜 성공 응답을 만들지 않는다.

Blob이란?

Blob은 Binary Large Object의 약자로, 브라우저가 사진·영상·음성 같은 바이너리 데이터를 메모리에서 다루는 형식입니다.

쉽게 말하면:

  • Blob: 촬영한 사진의 실제 데이터가 담긴 상자

  • File: 파일 이름과 수정 날짜가 추가된 Blob

  • object URL: Blob을 화면에 보여주기 위해 붙이는 임시 주소표

예를 들어 카메라로 촬영한 사진은 다음과 같이 존재합니다.

촬영 이미지
→ Blob으로 메모리에 보관
→ object URL을 만들어 화면에 미리보기
→ 제출할 때 Blob 자체를 서버로 전송
TypeScript
const previewUrl = URL.createObjectURL(imageBlob)

여기서 만들어지는 주소는 다음과 비슷합니다.

blob:https://whymath.com/임시식별자

이 주소는 인터넷에 올라간 이미지 주소가 아닙니다. 현재 브라우저가 메모리에 있는 Blob을 찾기 위한 임시 주소입니다. 따라서 API에는 object URL을 보내면 안 되고, FormData에 Blob을 담아 보내야 합니다.

사용을 끝낸 object URL은 메모리 누수를 막기 위해 해제합니다.

TypeScript
URL.revokeObjectURL(previewUrl)

Blob 자체에는 revoke를 호출하지 않습니다. Blob을 참조하는 상태를 null로 바꾸면 이후 브라우저가 메모리를 정리합니다.

위 결정들을 기존 분석 결과에 반영해 최종 구현 계획과 파일별 변경 범위를 갱신해줘. 아직 코드를 수정하거나 패키지를 설치하지 말고, 특히 다음을 먼저 명확히 보여줘.

  • 풀이 흐름 전용 Provider가 실제 라우터 구조에서 어디에 배치되는지

  • Blob 생성·리사이즈·미리보기·제출·정리 생명주기

  • shared-types와 validation 사이의 의존 방향

  • recognize와 solve의 최종 요청·응답 계약

  • 필기 유실 버그의 실제 원인과 최소 수정 범위

  • OpenAI Adapter가 공통 interface를 침범하지 않는 구조

갱신한 최종 계획을 보여준 뒤 구현하지 말고 승인을 기다려줘.

apps/
├─ web/   → React 기반 프론트엔드
└─ api/   → Express 기반 백엔드

Express란?

Express는 Node.js에서 백엔드 API 서버를 만드는 데 사용하는 가벼운 웹 프레임워크입니다.

예를 들어 프론트엔드가 AI에게 문제 인식을 요청하면 Express 서버가 다음과 같이 처리합니다.

TypeScript
app.post('/api/problems/recognize', async (req, res) => {
  // 1. 로그인 사용자 확인
  // 2. 이미지 검증
  // 3. AI Provider 호출
  // 4. 인식 결과 반환
})

Express 서버는 주로 다음을 담당합니다.

  • Supabase 로그인 토큰 검증

  • 이미지 Blob 수신

  • 이미지 크기와 형식 검증

  • OpenAI·Claude API 호출

  • AI API Key 보호

  • 요청 횟수 제한

  • 오류 및 타임아웃 처리

  • 추후 Supabase DB·Storage 연동

즉, 학생이 보는 화면은 apps/web, 화면 뒤에서 실제 처리를 담당하는 서버는 apps/api가 맡습니다.

Next.js API Route란?

Next.js API Route는 Next.js 프로젝트 내부에서 API를 만드는 기능입니다.

예를 들어 Next.js App Router에서는 다음과 같은 위치에 API를 작성합니다.

app/api/problems/recognize/route.ts
TypeScript
export async function POST(request: Request) {
  // 이미지 검증
  // AI 호출
  // 응답 반환
}

별도의 Express 서버를 만들지 않고, 하나의 Next.js 프로젝트 안에 화면과 API를 함께 둘 수 있다는 장점이 있습니다.

Next.js 앱
├─ 화면
├─ 서버 렌더링
└─ API Route

WhyMath에서 Express를 선택하는 이유

1. 현재 프론트엔드가 Next.js가 아니기 때문

WhyMath의 현재 apps/web은 기존 React 프론트엔드 구조로 구현되어 있습니다. Next.js API Route를 사용하려면 Next.js 런타임이 필요합니다.

API를 위해 Next.js를 새로 도입하면 다음 문제가 생깁니다.

  • 프론트엔드 빌드 구조와 라우팅 방식 변경 가능성

  • 새로운 프레임워크 의존성 추가

  • 기존 Vite 설정과 Next.js 설정의 중복

  • Auth, ProtectedRoute, ViewportGuard 회귀 위험

  • 사진·필기 기능을 불필요하게 옮기거나 수정할 가능성

Express를 사용하면 기존 apps/web은 그대로 두고 apps/api만 추가하면 됩니다.

2. 이미 확정한 모노레포 구조와 맞기 때문

현재 문서상 목표 구조는 프론트엔드와 백엔드를 별도 앱으로 구분합니다.

apps/web
apps/api
packages/shared-types
packages/validation

Express는 apps/api의 독립 서버로 정확히 들어맞습니다. 반면 Next.js API Route는 보통 Next.js 웹 앱 내부에 들어가기 때문에 이 구조와 맞지 않습니다.

3. AI API Key를 안전하게 분리할 수 있기 때문

OpenAI나 Claude의 API Key는 브라우저에 넣으면 안 됩니다. Express 서버의 환경변수에 두고 프론트엔드는 Express API만 호출해야 합니다.

Mermaid

이 구조에서는 AI Provider 변경, 인증, 파일 검증, 요청 제한을 모두 서버 내부에 감출 수 있습니다.

Next.js API Route도 API Key를 보호할 수 있지만, 현재 Next.js를 사용하지 않으므로 그것만을 위해 Next.js를 도입할 이유가 없습니다.

4. 이미지와 AI 요청을 독립적으로 관리하기 쉽기 때문

WhyMath 백엔드는 단순한 데이터 조회 API보다 다음처럼 처리할 것이 많습니다.

  • multipart/form-data 이미지 수신

  • Blob을 이미지 파일로 검증

  • 이미지 리사이즈 또는 정규화

  • Supabase access token 검증

  • AI 요청 timeout

  • Provider별 오류 변환

  • 요청 횟수 제한

  • recognize와 solve API 분리

Express에서는 이 처리들을 미들웨어와 서비스 계층으로 나누기 쉽습니다.

Route
→ 인증
→ 이미지 검증
→ 요청 스키마 검증
→ AI Adapter
→ 응답 변환

5. 기존 구현에 미치는 영향이 작기 때문

가장 중요한 이유입니다. 지금까지 완성한 사진 촬영, 직접쓰기, 로그인, 라우팅을 유지하면서 API만 추가할 수 있습니다.

프론트엔드에서는 대체로 다음 연결만 추가하면 됩니다.

현재 입력 상태
→ Blob 정규화
→ Express API 호출
→ 구조화된 응답 수신

전체 프론트엔드 프레임워크를 바꾸지 않아도 됩니다.

그렇다면 Next.js API Route가 안 좋은 방법인가?

그렇지는 않습니다. 프로젝트가 처음부터 Next.js라면 API Route가 좋은 선택일 수 있습니다.

예를 들어 다음 조건에서는 Next.js API Route가 더 간단합니다.

  • 프론트엔드가 이미 Next.js

  • 웹과 API를 하나의 앱으로 관리

  • API 규모가 작음

  • Vercel 같은 Next.js 친화적 환경에 배포

  • 별도 백엔드 서버가 필요하지 않음

하지만 WhyMath는 이미 React 프론트와 별도 apps/api를 전제로 개발하고 있습니다. 지금 Next.js API Route를 선택하면 기존 구조를 활용하는 것이 아니라 백엔드 기능을 위해 새로운 앱 구조를 하나 더 도입하는 상황이 됩니다.

결론

Express를 확정한다는 것은 기술적으로 더 최신이거나 무조건 우수해서가 아닙니다. 현재 WhyMath 구조에 가장 잘 맞고 변경 범위가 작기 때문입니다.

정리하면:

  • apps/web: 기존 React 화면 유지

  • apps/api: Express로 인증·이미지·AI 처리

  • packages/validation: API 요청·응답 검증

  • packages/shared-types: 프론트와 백엔드가 공유하는 도메인 타입

  • OpenAI·Claude: Express 내부 Adapter를 통해 호출

따라서 PRD의 Next.js API Route는 초기 기술 구조를 검토할 때 남은 이전 문구로 보고, 현재 실제 저장소와 PROJECT_STRUCTURE.md에 맞춰 Express로 갱신하는 것이 합리적입니다.
