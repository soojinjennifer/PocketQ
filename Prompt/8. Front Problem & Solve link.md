현재 캔버스에 직접 문제를 작성하고 실제 AI 풀이 결과를 받아 화면에 표시하는 것까지 구현했습니다.

기존 1~8단계 계획을 기준으로 보면 5단계 실제 OpenAI Provider 연결은 완료되었고, 6단계 프론트 문제 제출 연결은 기능적으로 연결되었지만 풀이 결과 화면에 Figma 디자인이 적용되지 않은 상태입니다.

따라서 지금은 7단계 Supabase 저장으로 넘어가지 말고, 6단계의 나머지 작업인 풀이 결과 UI 통합을 먼저 완료해야 합니다.

먼저 다음 자료와 코드를 분석해줘.

* `docs/PRD_WHYMATH.md`
* `FIGMA_SCREEN_MAP.md`
* `/solve` 화면과 관련 컴포넌트
* 문제 입력과 제출을 담당하는 코드
* SSE 또는 AI 풀이 응답을 처리하는 코드
* 현재 임시로 풀이 결과를 표시하는 컴포넌트
* Figma의 문제 풀이 결과 화면과 연결된 정확한 프레임·노드
* 기존 디자인 토큰과 공통 UI 컴포넌트

이번 응답에서는 코드를 수정하지 말고 다음 내용을 먼저 보고해줘.

1. 현재 캔버스 입력부터 AI 풀이 표시까지의 실제 데이터 흐름
2. 6단계에서 이미 완료된 부분과 미완료된 부분
3. 현재 결과 화면과 Figma 디자인의 차이
4. Figma 프레임의 영역별 컴포넌트 매핑
5. 새로 만들 파일과 수정할 파일
6. 재사용할 기존 컴포넌트와 디자인 토큰
7. `idle`, `recognizing`, `solving/streaming`, `success`, `error` 상태 처리 계획
8. 사진 입력과 직접쓰기 입력이 동일한 결과 컴포넌트를 사용하도록 하는 방법
9. 긴 풀이, 수식, 스크롤, iPad 반응형 처리 방법
10. 기존 기능의 회귀를 막기 위한 테스트 계획

구현 계획에는 다음 원칙을 반영해줘.

* 현재 정상 동작하는 캔버스 입력, 사진 입력, 인증, API 호출, OpenAI Adapter를 보존한다.
* 백엔드 API 계약을 불필요하게 변경하지 않는다.
* Figma 디자인을 임시 CSS로 덧붙이지 말고 기존 컴포넌트 구조와 디자인 토큰에 맞춰 구현한다.
* 사진과 직접쓰기 결과 화면을 별도로 중복 구현하지 않는다.
* AI 풀이의 임시 문자열이나 가짜 성공 응답을 사용하지 않는다.
* 스트리밍 중 들어오는 내용을 Figma 결과 영역에서 자연스럽게 누적 표시한다.
* 긴 문제와 긴 풀이가 잘리거나 화면 밖으로 넘치지 않게 한다.
* 수식과 LaTeX가 현재 어떤 방식으로 출력되는지 먼저 확인한다.
* 새로운 수식 렌더링 패키지가 필요하면 임의로 설치하지 말고 패키지명, 이유, 기존 대안, 영향 범위를 보고한다.
* Figma에 존재하는 화면과 상태를 우선 구현하고, 새로운 화면을 임의로 설계하지 않는다.
* 광범위한 리팩터링을 하지 않는다.
* Supabase 테이블, Storage, RLS와 환경변수는 이번 작업에서 변경하지 않는다.
* Git commit은 하지 않는다.

6단계 완료 조건도 계획에 명시해줘.

* 캔버스와 사진 입력 모두 실제 AI 풀이 결과 화면으로 연결된다.
* Figma의 레이아웃, 컴포넌트, 색상, 타이포그래피, 간격이 적용된다.
* 로딩·스트리밍·완료·오류 상태가 구분된다.
* 풀이가 길어져도 잘리지 않고 스크롤할 수 있다.
* 새 문제 제출 시 이전 풀이 상태가 정상적으로 초기화된다.
* typecheck, lint, test, build가 통과한다.
* 기존 사진 촬영과 직접쓰기 기능에 회귀가 없다.

분석 결과와 최종 구현 계획을 먼저 보여주고, 코드는 수정하지 말고 내 승인을 기다려줘.
