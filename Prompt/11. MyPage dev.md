# WhyMath 8단계 — 마이페이지 풀이 이력 및 이전 풀이 다시 보기 구현

WhyMath 프로젝트의 **8단계: MyPage 풀이 이력 조회 및 이전 풀이 다시 보기**를 진행한다.

현재까지 다음 단계는 완료된 상태다.

* 문제 입력
* 사진 촬영 / 직접쓰기
* AI 문제 인식 및 풀이
* ResultPanel 결과 화면
* 후속 질문 Chat Footer
* iPad Keyboard / Split View 대응
* Supabase 영구 저장

  * 문제
  * 풀이 결과
  * 후속 질문 대화
  * 사용자별 RLS

먼저 반드시 아래 문서와 현재 코드베이스를 확인한다.

* `docs/PRD_WHYMATH.md`
* `PLANNING.md`
* 최신 status / progress 관련 문서
* `/mypage` 관련 기존 구현
* Figma의 `4 · MyPage`
* 7단계에서 구현한 Supabase schema / migration / repository / API
* 현재 `/solve` ResultPanel 및 Chat UI

기존 구현을 깨뜨리지 않는 **최소 변경 방식**으로 진행한다.

---

# 1. 이번 단계의 목표

로그인 사용자가 지금까지 풀이한 문제를 `/mypage`에서 확인하고,

특정 기록을 선택하면

**문제 → AI 풀이 결과 → 당시 후속 질문 대화**

를 다시 확인할 수 있도록 한다.

핵심 사용자 흐름은 다음과 같다.

```text
/mypage
↓
풀이 이력 목록
↓
특정 문제 선택
↓
저장된 문제 + 풀이 + 후속 질문 조회
↓
이전 풀이 내용 다시 보기
```

이번 단계는 **저장된 데이터를 읽고 보여주는 기능**에 집중한다.

---

# 2. 먼저 현재 구조 분석

구현 전에 다음을 확인해서 간단히 보고한다.

1. 현재 `/mypage` 구현 상태
2. Figma MyPage 구조
3. 7단계 Supabase 테이블 관계
4. 풀이 목록 조회에 사용할 기존 API / repository
5. 풀이 상세 조회에 사용할 기존 API / repository
6. ResultPanel 컴포넌트 재사용 가능 범위
7. 수정하거나 추가해야 할 파일 목록

기존 코드가 있다면 새 구조를 만들지 말고 최대한 재사용한다.

---

# 3. 풀이 이력 목록

`/mypage`에서 로그인 사용자의 풀이 기록을 조회한다.

기본 정렬:

```text
최신 풀이
↓
이전 풀이
↓
오래된 풀이
```

각 기록에서는 Figma와 PRD를 기준으로 필요한 최소 정보만 표시한다.

예:

* 문제 내용
* 풀이 날짜
* 입력 방식이 디자인상 필요하면 사진 / 직접쓰기 구분
* 필요한 상태 또는 간단한 메타 정보

문제 텍스트가 길다면 UI가 깨지지 않도록 적절히 제한한다.

단, 임의로 새로운 카드 디자인을 만들지 않는다.

**Figma `4 · MyPage`를 기준으로 구현한다.**

---

# 4. 풀이 상세 조회

사용자가 풀이 기록을 선택하면 해당 풀이의 전체 데이터를 불러온다.

조회 대상:

```text
problem / solve session
├─ recognized problem
├─ solution
│   ├─ answer
│   ├─ concept
│   └─ steps
└─ chat_messages[]
```

후속 질문은 반드시 저장된 순서를 유지한다.

예:

```text
user
assistant
user
assistant
```

message timestamp가 존재한다면 안정적인 ordering 기준을 사용한다.

---

# 5. 기존 Result UI 재사용

이전 풀이 상세 화면을 위해 기존 풀이 UI를 복제하지 않는다.

가능한 경우 현재 `/solve`에서 사용하는 다음 컴포넌트를 재사용한다.

* ResultPanel
* ResultCard
* AnswerBox
* RecognizedProblemBar
* Badge
* ChatBubble 또는 후속 대화 표시 관련 컴포넌트

단, **과거 풀이 조회 모드(read-only)** 와 현재 새 문제 풀이 상태를 명확히 분리한다.

예:

```text
현재 풀이
→ interactive

이전 풀이 조회
→ read-only
```

과거 기록을 열었다고 해서 새로운 풀이 state를 덮어쓰거나 현재 `/solve` session을 오염시키면 안 된다.

---

# 6. 후속 질문 처리 범위

이번 단계에서는 **과거 대화를 다시 보는 것**을 우선 구현한다.

과거 풀이에서 다시 후속 질문을 이어서 입력할 수 있는 기능은 PRD 요구사항을 확인한다.

PRD에 명확하게 요구되어 있지 않다면 이번 단계에서는:

```text
이전 후속 질문 표시 = 구현
새 후속 질문 이어쓰기 = 제외
```

로 처리한다.

기능 범위를 임의로 확대하지 않는다.

---

# 7. 데이터 조회 구조

React component에서 Supabase query를 직접 여러 곳에 작성하지 않는다.

7단계에서 구축한 구조를 그대로 사용한다.

예:

```text
UI
↓
hook / service
↓
API
↓
repository
↓
Supabase
```

또는 현재 실제 코드베이스의 구조를 따른다.

필요하면 다음 수준의 기능을 제공한다.

```text
getSolveHistory()
getSolveDetail(id)
```

단, 실제 naming은 기존 프로젝트 규칙에 맞춘다.

---

# 8. 사용자 보안

모든 조회는 현재 로그인 사용자 기준이어야 한다.

사용자 A가 URL이나 ID를 임의로 변경하여 사용자 B의 풀이를 조회할 수 없어야 한다.

기존 Supabase RLS를 유지하고, frontend에서 user ID를 신뢰하여 보안을 대신하지 않는다.

다음을 반드시 검증한다.

```text
auth.uid() = user_id
```

---

# 9. Loading / Empty / Error 상태

다음 상태를 구현한다.

## Loading

풀이 기록을 불러오는 중이라는 것을 기존 디자인 시스템 방식으로 표시한다.

새로운 로딩 UI를 임의 설계하지 않는다.

## Empty

풀이 기록이 없는 사용자는 빈 화면이 아니라 적절한 empty state를 보여준다.

가능하면 다음 행동으로 자연스럽게 연결한다.

```text
아직 풀이 기록이 없음
→ 문제 풀러 가기
```

## Error

조회 실패 시 화면 전체가 깨지지 않아야 한다.

기술적인 Supabase 오류 메시지를 그대로 사용자에게 노출하지 않는다.

---

# 10. 반응형

기존 WhyMath 기준을 유지한다.

특히 다음을 확인한다.

* iPad Landscape
* iPad Portrait가 지원 대상이면 해당 상태
* Split View
* 좁은 viewport
* 긴 문제 텍스트
* 긴 수식
* 후속 질문이 많은 기록

Figma의 절대 좌표를 그대로 복사하지 말고 반응형 layout으로 변환한다.

---

# 11. 이번 단계에서 하지 않을 것

이번 단계에서는 아래 기능을 구현하지 않는다.

* 풀이 기록 삭제
* 즐겨찾기
* 폴더
* 태그
* 검색
* 정렬 옵션 UI
* pagination 고도화
* infinite scroll
* analytics
* 문제 공유
* PDF 다운로드
* 과거 풀이 수정
* 새로운 디자인 redesign
* Supabase Realtime

데이터 양이 현재 MVP 수준에서 적다면 pagination을 미리 과도하게 구현하지 않는다.

# 12. 주요 테스트 시나리오

## Case 1

사용자 A가 문제를 3개 푼다.

`/mypage`에 3개 기록이 최신순으로 표시된다.

---

## Case 2

특정 문제를 선택한다.

저장된:

* 문제
* 답
* 개념
* 단계별 풀이

가 올바르게 표시된다.

---

## Case 3

후속 질문을 여러 번 했던 풀이를 연다.

user / assistant 대화가 기존 순서 그대로 표시된다.

---

## Case 4

새로고침 후에도 같은 풀이 이력이 조회된다.

---

## Case 5

사용자 A는 사용자 B의 풀이를 조회할 수 없다.

---

## Case 6

풀이 기록이 없는 계정에서는 Empty State가 정상적으로 표시된다.

---

## Case 7

긴 문제, 긴 수식, 긴 후속 대화에서도 레이아웃이 깨지지 않는다.

---

## Case 8

iPad Split View에서도 목록과 상세 콘텐츠가 viewport 밖으로 잘리지 않는다.

---

# 13. Regression 확인

이번 구현으로 기존 다음 기능이 깨지지 않아야 한다.

* `/solve`
* 사진 입력
* 직접쓰기
* AI 풀이
* ResultPanel
* 후속 질문
* Chat Footer
* Keyboard 대응
* Supabase 저장

특히 과거 풀이 조회 때문에 현재 `/solve` state가 변경되지 않는지 확인한다.

---

# 14. 최종 검증

현재 package script를 확인한 뒤 실제 프로젝트에서 사용하는 명령으로 다음을 수행한다.

```text
typecheck
lint
test
build
```

기존 테스트 실패와 이번 변경으로 발생한 regression을 구분한다.

가능하다면 이번 단계의 repository/API 관련 테스트도 추가한다.

# 완료 조건

다음 조건이 모두 충족되어야 8단계를 완료로 판단한다.

> 로그인한 사용자가 `/mypage`에서 자신의 과거 풀이 목록을 볼 수 있고, 특정 풀이를 선택하면 저장되어 있는 문제·AI 풀이·후속 질문 전체 내용을 다시 확인할 수 있다.

추가로:

* 새로고침해도 데이터가 유지된다.
* 다른 사용자의 데이터는 볼 수 없다.
* 기존 `/solve` 흐름에는 regression이 없다.
* iPad 및 Split View에서 정상적으로 사용할 수 있다.

완료되지 않은 항목은 완료되었다고 보고하지 않는다.
