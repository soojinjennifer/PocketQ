[사용 에이전트: plan-agent + design-agent]

`plan-agent`를 주 분석 담당으로 사용하고, Figma 디자인·Pen Rail 상태·반응형·iPad 입력·접근성 검수는 `design-agent`를 사용해 함께 분석해줘.

두 에이전트의 결과를 따로 나열하지 말고, 충돌 여부를 확인한 하나의 통합 구현 계획으로 정리해줘.

이번 단계의 목표는 `/solve`의 `직접쓰기` 입력 방식을 실제로 사용할 수 있도록 필기 캔버스와 Pen Rail 도구의 구현 계획을 수립하는 것이다.

현재는 읽기 전용 분석만 수행하고, 아직 `development-agent`를 사용하거나 코드를 수정하지 마.

## 1. 현재 완료된 기준 상태

다음 작업은 이미 구현되고 검증되었다.

* `/solve`의 Pen Rail `사진` 버튼에서 `/camera`로 이동
* `/camera`에서 촬영
* `/camera/preview`에서 재촬영 또는 사진 사용
* 사진 사용 후 `/solve`로 복귀
* 라우터 state로 촬영 이미지 전달
* `ProblemCard`에 실제 촬영 사진 표시
* `ProblemCard`의 사진 있음·인식 실패·사진 없음 상태
* 사진이 없거나 선택 문제가 0개이면 `풀기` 버튼 비활성화
* `Button`의 pill-dark·primary·glass·disable 스타일
* `Modal`의 error 아이콘
* Pen Rail의 실제 Figma 벡터 아이콘 적용
* typecheck, lint, test 78/78, build 통과

위 기능을 다시 만들거나 구조를 임의로 변경하지 말고, 실제 현재 코드를 확인한 후 기존 구현을 보존하는 계획을 세워줘.

현재 Pen Rail에서 사진 버튼을 제외한 나머지 도구 아이콘은 표시만 되고 실제 동작은 아직 없다.

## 2. 이번 분석 범위

### 2.1 직접쓰기 입력 모드

`/solve`에서 직접쓰기 방식을 선택했을 때 Figma에 정의된 필기 영역을 표시하고, 사용자가 Apple Pencil·터치·마우스로 문제를 직접 쓸 수 있는 구조를 계획한다.

다음을 확인해줘.

* 현재 입력 모드 상태의 실제 구현 위치와 타입
* `camera`와 `handwriting` 모드 전환 구조
* 직접쓰기 선택 시 표시되는 정확한 Figma 화면
* 필기 캔버스의 크기·배경·border·radius·간격
* 사진 입력 UI와 필기 UI의 교체 방식
* 모드 전환 시 기존 촬영 사진과 필기 데이터의 유지 또는 삭제 기준
* 유효한 필기 입력의 판단 기준
* 필기가 없을 때와 있을 때 `풀기` 버튼 상태
* 필기 내용을 `ProblemCard` 또는 현재 문제 입력 영역에 표시하는 방식

PRD나 Figma에 근거가 없다면 사진이나 필기 데이터를 임의로 삭제하는 동작을 계획하지 말고, 결정이 필요한 사항으로 보고해줘.

### 2.2 Pen Rail 도구

현재 코드와 최신 Figma에서 Pen Rail의 각 버튼을 확인하고, 아이콘 이름만 보고 동작을 추측하지 마.

최소한 다음을 분석해줘.

* 각 버튼의 Figma 원본 이름
* 화면에 표시된 순서
* 정확한 의미와 예상 동작
* 기본 선택 도구
* 선택·비선택·hover·active·disabled 상태
* 툴팁 또는 접근 가능한 이름
* 버튼별로 필요한 상태
* 이미 구현된 사진 버튼과의 관계
* 펜
* 지우개
* 되돌리기·초기화·삭제 중 실제 Figma가 의미하는 동작
* 취소 또는 닫기 아이콘의 실제 동작

Figma나 PRD에 없는 기능, 확인 팝업, 토스트, 임의 문구를 추가하지 마.

`Icon/Refresh`가 실행 취소인지 전체 초기화인지, `Icon/Cancel`이 필기 전체 삭제인지 입력 모드 종료인지 반드시 근거를 확인하고, 확인할 수 없으면 사용자 결정 항목으로 남겨줘.

### 2.3 필기 캔버스 기술 구조

신규 캔버스 라이브러리를 바로 도입하지 말고, 기존 의존성과 브라우저 기본 기능으로 구현 가능한지 먼저 분석해줘.

다음을 포함해 계획해줘.

* Pointer Events 기반 입력 가능 여부
* `pointerType`의 pen·touch·mouse 처리
* Apple Pencil 입력
* 필요한 경우 pressure 값 사용 여부
* pointer capture 적용 여부
* 캔버스 밖으로 이동하거나 `pointercancel`이 발생했을 때 처리
* iPad에서 필기 중 페이지 스크롤과 확대가 발생하지 않게 하는 범위
* 손바닥 접촉 오입력에 대한 브라우저 수준 대응과 한계
* CSS 표시 크기와 canvas 내부 해상도의 분리
* `devicePixelRatio`를 고려한 선명도
* 1194×834와 1024~1193px에서 좌표 보정
* 화면 크기 변경 시 필기 데이터 보존
* 세로모드 및 Split View에서 기존 `ViewportGuard`와의 관계
* `prefers-reduced-motion` 영향 여부

## 3. 필기 데이터 상태

필기 결과를 단순히 캔버스 픽셀에만 저장할지, 획 데이터로 관리할지 현재 구조와 다음 단계의 AI 입력을 고려해 비교해줘.

예상 가능한 구조는 다음과 같지만 그대로 강제하지 않는다.

```ts
type HandwritingPoint = {
  x: number
  y: number
  pressure?: number
  timestamp: number
}

type HandwritingStroke = {
  id: string
  tool: 'pen' | 'eraser'
  points: HandwritingPoint[]
}
```

다음을 분석 보고에 포함해줘.

* 상태의 소유 위치
* 페이지와 feature 컴포넌트의 책임
* 획 데이터와 렌더링의 분리 여부
* undo 또는 reset 구현에 필요한 상태
* 모드 전환 시 데이터 생명주기
* 컴포넌트 해제와 라우트 이동 시 처리
* 이후 OCR·AI 연동에서 사용할 수 있는 출력 경계
* 향후 Blob 또는 이미지로 변환할 위치
* 현재 단계에서 이미지 변환까지 구현할 필요가 있는지
* 새로고침 시 필기 데이터가 사라져도 되는지
* 전역 상태 라이브러리 없이 구현 가능한지

실제 OCR, AI API 호출, 서버 업로드와 DB 저장은 이번 범위에 포함하지 않는다.

## 5. 구조 원칙

* pages는 UI와 feature를 조립한다.
* 필기 상태와 입력 로직은 적절한 feature 영역에 둔다.
* 페이지 컴포넌트에 Pointer Event와 캔버스 로직을 몰아넣지 않는다.
* 기존 공통 컴포넌트를 우선 재사용한다.
* 화면 전용 필기 컴포넌트를 근거 없이 `shared/ui`로 승격하지 않는다.
* 공통 컴포넌트 수정이 필요하면 다른 화면에 미치는 영향을 보고한다.
* 기존 사진 촬영 흐름을 보존한다.
* 기존 Auth, ProtectedRoute, ViewportGuard를 보존한다.
* TypeScript strict를 준수하고 `any` 사용을 계획하지 않는다.
* 임의 색상·픽셀값·SVG·디자인 토큰을 추가하지 않는다.
* 승인되지 않은 신규 직접 의존성을 추가하지 않는다.
* Figma export 코드를 그대로 사용하지 않는다.
* 한 화면 전체를 하나의 컴포넌트로 만드는 계획을 세우지 않는다.
