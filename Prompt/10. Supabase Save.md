# WhyMath 7단계 — Supabase 영구 저장 구현 프롬프트

WhyMath 프로젝트의 **7단계: Supabase 영구 저장(Persistence)** 을 진행한다.

현재까지 **6.5단계 후속 질문 Chat Footer와 iPad Keyboard / Split View 대응까지 완료된 상태**다.

먼저 다음 문서와 현재 코드베이스를 반드시 확인하고, 기존 구현을 깨뜨리지 않는 최소 변경 방식으로 작업한다.

* `docs/PRD_WHYMATH.md`
* `PLANNING.md`
* 현재 개발 상태를 기록한 관련 status / progress 문서
* Supabase 관련 기존 설정 및 migration
* 현재 `/solve` 문제 입력 → AI 풀이 → 후속 질문 대화 흐름
* 현재 frontend / API / shared type 구조

## 1. 이번 단계의 목표

현재 브라우저 메모리 또는 React state에만 존재하는 다음 데이터를 **Supabase에 사용자별로 영구 저장**할 수 있도록 구현한다.

### 저장 대상

1. 사용자가 입력한 문제

   * 사진 입력 / 직접쓰기 입력 구분
   * 인식된 문제 텍스트
   * 필요한 최소 입력 메타데이터

2. AI 풀이 결과

   * 최종 답
   * 개념 설명
   * 단계별 풀이
   * 생성 시각
   * 사용한 모델 또는 provider 정보가 현재 구조상 필요하면 저장

3. 후속 질문 대화

   * user / assistant 역할
   * message content
   * message 순서
   * 생성 시각
   * 어떤 문제/풀이에 속한 대화인지 관계 유지

4. 사용자 관계

   * Supabase Auth의 현재 로그인 사용자와 모든 풀이 기록을 연결한다.
   * 다른 사용자의 데이터에 접근할 수 없어야 한다.

---

## 2. 핵심 설계 원칙

### A. 기존 구조 우선

새로운 구조를 임의로 크게 만들지 말고 현재 프로젝트의:

* `apps/web`
* API 계층
* shared types
* validation
* contracts

구조를 먼저 확인한 후 기존 패턴을 확장한다.

이미 동일 목적의 type, schema, repository, API가 있다면 반드시 재사용한다.

---

### B. DB schema

현재 Supabase schema를 먼저 확인한다.

필요한 테이블이 없다면 다음 개념을 기준으로 최소한의 schema를 설계한다.

예:

* `problems`
* `solutions`
* `chat_messages`

단, 현재 프로젝트 구조상 `solve_sessions` 또는 하나의 상위 엔티티를 두는 것이 더 적절하다면 그 이유를 설명한 뒤 기존 구조와 가장 잘 맞는 방식을 선택한다.

관계 예시는 다음을 만족해야 한다.

```text
user
 └─ problem / solve session
      ├─ solution
      └─ chat_messages[]
```

각 테이블에는 최소한 다음을 검토한다.

* `id`
* `user_id`
* 관계 foreign key
* `created_at`
* 필요한 경우 `updated_at`

불필요하게 많은 필드는 만들지 않는다.

---

## 3. RLS / Security

Supabase RLS를 반드시 적용한다.

기본 원칙:

```text
auth.uid() = user_id
```

사용자는 자신의 문제, 풀이, 후속 질문만:

* INSERT
* SELECT
* 필요한 경우 UPDATE / DELETE

할 수 있어야 한다.

Service Role Key를 frontend에 노출하지 않는다.

Browser client에서 접근해야 하는 데이터와 server/API에서 처리해야 하는 데이터를 명확히 구분한다.

---

## 4. 저장 시점

현재 `/solve` 흐름을 분석한 뒤 아래 lifecycle을 구현한다.

### 최초 풀이

```text
문제 입력
→ AI 풀이 요청
→ 풀이 성공
→ problem/solve session 생성
→ solution 저장
```

### 후속 질문

```text
사용자 질문
→ user message 저장
→ AI 답변 생성
→ assistant message 저장
```

단, AI 응답이 streaming 방식이라면 **부분 chunk마다 DB에 저장하지 않는다.**

최종 assistant message가 완성된 시점에 한 번 저장하는 것을 기본으로 한다.

---

## 5. 실패 처리

DB 저장 실패 때문에 이미 생성된 AI 풀이 화면 전체가 사라져서는 안 된다.

다음 상황을 구분한다.

```text
AI 풀이 성공 + DB 저장 성공
AI 풀이 성공 + DB 저장 실패
AI 풀이 실패
후속 질문 성공 + DB 저장 실패
```

저장 실패 시:

* 사용자에게 과도한 기술 오류를 노출하지 않는다.
* console/server log에는 원인 추적이 가능해야 한다.
* 동일 요청이 중복 저장되지 않도록 고려한다.

---

## 6. 이미지 / Canvas 데이터 처리

사진이나 직접쓰기 PNG를 Supabase에 영구 저장할 필요가 있는지 먼저 PRD와 현재 구조를 확인한다.

이번 단계에서는 **향후 풀이 기록을 다시 열기 위해 꼭 필요한 데이터만 저장**한다.

이미지 원본 저장이 PRD에 명확히 요구되지 않는다면:

* 원본 Blob/Base64를 DB column에 직접 저장하지 않는다.
* 인식된 문제 텍스트 중심으로 저장한다.
* 필요 시 Storage 도입은 별도 단계로 분리한다.

임의로 Supabase Storage까지 scope를 확대하지 않는다.

---

## 7. API / Repository Layer

DB 접근 코드를 React component 내부에 직접 흩뿌리지 않는다.

현재 프로젝트 구조에 맞춰:

```text
UI
→ hook/service
→ API
→ repository/data access
→ Supabase
```

또는 현재 코드베이스가 사용하는 가장 가까운 구조를 따른다.

공통 type과 validation schema가 있다면 frontend/backend에서 재사용한다.

---

## 8. 기존 UX 유지

이번 7단계에서는 다음 UI를 새로 redesign하지 않는다.

* ResultPanel
* ResultCard
* AnswerBox
* RecognizedProblemBar
* 후속 질문 Footer
* iPad Keyboard 대응
* Split View 대응

7단계의 목적은 **Persistence 연결**이다.

기존 6.5단계 UI와 interaction이 깨지지 않아야 한다.

---

## 9. 이번 단계에서 하지 않을 것

다음은 scope에서 제외한다.

* `/mypage` 전체 UI 구현
* 풀이 이력 목록 UI
* 풀이 상세 화면 redesign
* 삭제/즐겨찾기/폴더 기능
* 검색
* pagination
* analytics
* 이미지 Storage 고도화
* 실시간 Supabase Realtime
* 불필요한 caching 시스템

이 기능들은 저장 기반이 안정화된 이후 단계에서 진행한다.

---

## 10. 테스트

최소 다음 시나리오를 검증한다.

### Case 1

로그인 사용자 A가 문제를 풀면 Supabase에 해당 사용자 ID로 저장된다.

### Case 2

풀이 결과의 answer / concept / steps가 새로고침 후에도 DB에 남아 있다.

### Case 3

후속 질문을 3회 하면 메시지 순서와 role이 올바르게 저장된다.

### Case 4

사용자 A가 사용자 B의 데이터를 조회할 수 없다.

### Case 5

DB 저장 실패가 발생하더라도 이미 생성된 풀이 화면이 비정상적으로 사라지지 않는다.

### Case 6

같은 풀이가 의도치 않게 두 번 저장되지 않는다.

---

## 11. 최종 검증

구현 후 반드시 프로젝트에서 사용하는 실제 명령을 확인하여 다음을 실행한다.

```text
typecheck
lint
test
build
```

기존 테스트가 실패하면 기존 오류인지 이번 변경으로 발생한 regression인지 구분한다.

---

## 12. 작업 방식

바로 코드를 대규모 수정하지 말고 먼저 현재 상태를 분석한다.

먼저 아래 내용을 간단히 보고한다.

1. 현재 solve / chat 데이터가 어디에서 관리되고 있는지
2. 현재 Supabase 관련 구조
3. 기존 DB schema
4. 7단계에서 수정할 파일 목록
5. 추가할 migration/schema
6. 데이터 저장 lifecycle
7. 예상되는 위험 요소

그 다음 **최소 변경 계획을 세운 후 구현한다.**

구현이 끝나면 다음 형식으로 결과를 보고한다.

```text
7단계 구현 결과

1. DB schema / migration
2. RLS 정책
3. 문제 저장
4. 풀이 결과 저장
5. 후속 질문 저장
6. 수정한 주요 파일
7. 테스트 결과
8. 남아 있는 이슈
9. 다음 8단계로 넘길 항목
```

중요:

* 기존 동작을 깨뜨리지 않는다.
* PRD에 없는 기능을 임의로 확대하지 않는다.
* 현재 architecture와 naming convention을 따른다.
* 이미 존재하는 구현을 중복 생성하지 않는다.
* Supabase 관련 secret을 frontend에 노출하지 않는다.
* 완료되지 않은 항목을 완료되었다고 보고하지 않는다.
