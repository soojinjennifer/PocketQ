## 0. 요약 (Executive Summary)

기존 8단계 문제 DB 구축 로드맵은 **"좋은 문제를 많이 만드는 것"** 을 목표로 삼고 있습니다. 그러나 이 방식으로는 서비스의 본래 가치인 **"학생이 막힌 그 지점에서, 학생이 쓰던 방법 그대로 이어서 가르쳐 주는 것"** 을 구현할 수 없습니다. 문제 DB는 *문제*에 대한 지식이지 *학생의 풀이*에 대한 지식이 아니기 때문입니다.

본 제안서는 서비스의 중심축을 다음과 같이 전환할 것을 제안합니다.

| 구분 | As-Is (현행 계획) | To-Be (전환 후) |
|---|---|---|
| 핵심 질문 | "이 유형의 문제를 어떻게 만들 것인가" | "이 학생의 풀이는 어디서, 왜 막혔는가" |
| 입력 데이터 | 문제 (사진·필기) | 문제 + **학생이 직접 쓴 풀이 과정** |
| AI의 역할 | 정답 풀이를 생성하는 해설자 | **풀이를 진단하고 이어 쓰는 과외 선생님** |
| 구축 자산 | Problem Family DB, 난이도 모델 | **해법 카탈로그 · 개념 그래프 · 오류 유형 분류표** |
| 경쟁 지형 | 대형 문제은행 사업자와 정면 경쟁 | 국내 미개척 영역, 데이터 해자 형성 가능 |
| 선투자 규모 | 대규모 문항 수집·가공 (수만 문항) | **소규모 고밀도 지식 자산** (수백 건 단위) |

전환의 실질적 이점은 세 가지입니다.

1. **차별성** — 정답 해설은 이미 시장에 흔합니다. "네가 쓴 두 번째 줄까지는 맞았고, 세 번째 줄에서 판별식 조건을 빠뜨렸다"는 진단은 사람 과외 선생님만 해 주던 일입니다.
2. **데이터 해자** — 학생이 손으로 쓴 풀이 과정과 그 오류 패턴은 어떤 문제은행에도 존재하지 않는 데이터입니다. 서비스 운영 자체가 학습 데이터를 축적하는 구조가 됩니다.
3. **공수 절감** — 초기 구축 자산이 문항 수만 건에서 개념·해법·오류 유형 수백 건으로 줄어듭니다. 기존 8단계 대비 초기 공수를 대폭 축소하면서 MVP를 앞당길 수 있습니다.

## 1. 왜 현행 8단계로는 안 되는가

현행 계획의 각 단계는 다음 목적을 갖습니다.

```
STEP 1~3  교육과정·평가원 예시문항·기출 매핑    → 문제의 좌표계
STEP 4~5  Problem Family DB, 난이도 모델        → 문제의 분류·난이도
STEP 6~7  생성 템플릿, 자동 검증·품질 필터      → 문제의 대량 생산
STEP 8    학생 데이터로 적중률 보정              → 문제의 정밀화
```

여덟 단계가 모두 **문제(problem)** 를 향해 있습니다. 여기서 산출되는 자산으로는 다음 질문에 답할 수 없습니다.

- 학생이 세 줄을 썼는데 **어느 줄부터 틀렸는지** — 문제 DB에는 학생의 풀이가 없습니다.
- 학생이 **어떤 공식을 쓰려던 것인지** — 문제 DB는 정답 해법 1개만 담습니다.
- 같은 문제를 **다른 방법으로 풀면 어떻게 되는지** — 다해법 정보가 스키마에 없습니다.
- 막힌 곳이 **어떤 선수 개념의 결손 때문인지** — 단원 태그만으로는 역추적이 불가능합니다.

즉 현행 8단계는 **"유사 문제를 더 주는 서비스"** 의 인프라이며, 목표하시는 **"막힌 곳을 풀어 주고 다양한 해법을 제안하는 튜터"** 의 인프라가 아닙니다. 두 인프라는 재사용 가능한 부분이 일부(교육과정 체계, 수식 검증기) 있을 뿐 대부분 별개입니다.

## 2. 전환 후의 서비스 핵심 — 5단계 튜터링 루프

```
① 문제 입력            사진 촬영 또는 Apple Pencil 필기
        ↓
② 내 풀이 입력          "풀 수 있는 데까지 써 보기" (한 줄만 써도 무방)
        ↓
③ 풀이 진단            어디까지 맞았는가 / 어디서 막혔는가 / 왜 막혔는가
        ↓
④ 이어풀기 모드 선택    [내 방법으로 계속]  [다른 방법으로]  [개념부터 다시]
        ↓
⑤ 대화형 심화          후속 질문 → 궁금증 해소 → (선택) 유사 문제
```

### 2.1 각 단계의 사용자 가치

**② 내 풀이 입력** — 이 단계가 신설되는 핵심 화면입니다. 학생은 문제 옆 캔버스에 자신이 푼 데까지 씁니다. "모르겠어요" 버튼도 함께 두어, 아무것도 못 쓴 학생은 곧바로 ③으로 넘어갑니다.

**③ 풀이 진단** — 결과 화면 최상단에 다음 세 가지가 표시됩니다.

- **여기까지는 맞았어요** — 학생 풀이의 유효 구간을 초록으로 표시합니다.
- **여기서 막혔어요** — 최초 오류 줄 또는 중단 줄을 표시합니다.
- **왜 막혔는지** — 오류 유형(부호 오류·조건 누락·공식 오적용 등)과 관련 개념을 한 문장으로 설명합니다.

**④ 이어풀기 모드** — 서비스 정체성을 결정하는 분기입니다.

| 모드 | 동작 | 예시 |
|---|---|---|
| 내 방법으로 계속 | 학생이 쓰던 해법을 그대로 유지한 채, 마지막 유효 줄을 출발점으로 이어서 풀어 줍니다. | 학생이 완전제곱식으로 가고 있었다면 미분으로 바꾸지 않고 완전제곱식으로 끝냅니다. |
| 다른 방법으로 | 같은 문제에 적용 가능한 다른 해법을 2~3개 제시하고, 선택한 해법으로 처음부터 풀어 줍니다. | 완전제곱식 / 그래프 대칭성 / (고2 이상) 미분 |
| 개념부터 다시 | 막힌 지점에 연결된 개념과 그 선수 개념을 먼저 설명한 뒤 풀이로 넘어갑니다. | "판별식이 왜 실근의 개수를 결정하는지"부터 설명 |

**⑤ 유사 문제** — 우선순위를 낮춰 v1.2로 이관합니다. 다만 진단 결과(오류 유형·취약 개념)가 축적되면 **"틀린 이유에 맞춘 유사 문제"** 를 추천할 수 있게 되어, 오히려 나중에 훨씬 강력한 기능이 됩니다.

## 3. PRD 섹션별 변경 델타

기존 `PRD_WHYMATH.md` v1.1을 기준으로 한 개정 방향입니다. PRD v2.0 작성 시 이 표를 그대로 반영합니다.

### 3.1 1장 개요

| 항목 | 조치 | 개정 방향 |
|---|---|---|
| 1.1 배경 및 문제 정의 | **수정** | "정답 풀이를 볼 곳은 많지만, **내가 쓴 풀이를 봐 주는 곳은 없다**"로 문제 정의를 재설정합니다. 학원·인강·기존 검색 서비스는 모두 *표준 정답 풀이*를 제공할 뿐, 학생 개인의 풀이 경로를 읽고 그 경로 위에서 지도해 주지 않는다는 점을 명시합니다. |
| 1.2 제품 목표 | **교체** | ① 학생이 쓴 풀이의 막힌 지점을 정확히 찾아 준다 ② 학생이 선택한 해법을 존중하여 이어서 풀어 준다 ③ 하나의 문제에 대해 복수의 해법을 학년 범위 안에서 제시한다 ④ 막힌 지점을 개념 결손으로 역추적하여 설명한다 |
| 1.3 대상 사용자 | 유지 | 중1~고3, iPad + Apple Pencil |
| 1.4 성공 지표 | **교체** | 아래 3.1.1 참조 |

#### 3.1.1 성공 지표 개정안 (MVP 기준)

| 지표 | 정의 | 목표 |
|---|---|---|
| 풀이 입력률 | 문제 입력 후 자기 풀이를 1줄 이상 작성한 세션 비율 | 60% 이상 |
| 진단 정확도 | 교사 라벨 대비 막힌 지점(줄 번호) Top-1 일치율 | 85% 이상 |
| 오류 유형 분류 정확도 | 교사 라벨 대비 오류 유형 F1 | 0.75 이상 |
| 이어풀기 채택률 | 진단 확인 후 이어풀기 모드를 1회 이상 선택한 비율 | 70% 이상 |
| 다해법 탐색률 | "다른 방법으로"를 1회 이상 선택한 세션 비율 | 25% 이상 |
| 이해 완료율 | 세션 종료 시 "이해했어요" 응답 비율 | 65% 이상 |
| 주간 재방문율 | 가입 후 7일 내 재방문 비율 | 50% 이상 |

기존 지표 중 "풀이 완료율", "풀이 응답 시간(5초)"은 유지하되, 진단 단계가 추가되므로 첫 응답 목표를 **7초**로 완화합니다.

### 3.2 2장 페르소나 및 시나리오

**2.2 핵심 시나리오를 전면 재작성합니다.**

> 1. 지민이 이차함수 최댓값 문제를 촬영합니다.
> 2. "내 풀이 쓰기" 캔버스에 자신이 푼 세 줄을 Apple Pencil로 씁니다. 판별식을 쓰려다 부호에서 막혔습니다.
> 3. "봐 주세요"를 누릅니다.
> 4. 진단 결과가 표시됩니다. **"2번째 줄까지는 정확합니다. 3번째 줄에서 부등호 방향이 반대로 적용되었습니다."**
> 5. 지민이 **[내 방법으로 계속]** 을 선택합니다. AI는 판별식 접근을 유지한 채 3번째 줄부터 바로잡아 끝까지 풀어 줍니다.
> 6. 지민이 **[다른 방법으로]** 를 눌러 봅니다. "완전제곱식으로 푸는 법", "그래프 대칭축으로 푸는 법" 두 가지가 제시되고, 각각의 장단점이 한 줄씩 설명됩니다.
> 7. "왜 꼭짓점에서 최댓값이 되는지" 후속 질문을 던지고 답을 받습니다.
> 8. 이 문제는 "이차함수 > 최대·최소" 개념 + "부등호 방향 오류" 유형으로 분류되어 마이페이지에 저장됩니다.

### 3.4 4장 기능 요구사항 — 신설·수정 요구사항군

기존 ID 체계(AUTH / GRADE / INPUT / SOLVE / CHAT / MYPAGE / PROV)와 충돌하지 않도록 **신규 4개 군**을 추가합니다.

| WORK-2 | 학생 풀이는 **줄 단위(line-level)로 분할 인식**되어, 각 줄이 개별 LaTeX 수식으로 구조화된다. | P0 |
| WORK-3 | 인식 결과를 줄 번호와 함께 학생에게 보여 주고, 오인식 줄을 개별 수정할 수 있게 한다. 인식 신뢰도가 낮은 줄은 시각적으로 표시한다. | P0 |

| WORK-6 | 풀이 캔버스는 세로 스크롤이 가능하여 긴 풀이도 입력할 수 있다. | P1 |

| ID | 요구사항 | 우선순위 |
|---|---|---|

| DIAG-4 | 오류가 없고 단순히 중단된 경우("어디까지 맞았지만 다음 단계를 모름")와 오류가 있는 경우를 구분하여 다른 문구로 안내한다. | P0 |
| DIAG-5 | 진단 신뢰도가 임계값 미만이면 단정하지 않고 "이 부분을 다시 확인해 볼까요"로 완화 표현한다. 오진단으로 학생을 혼란시키지 않는다. | P0 |
| DIAG-6 | 학생 풀이가 정답에 도달했으나 표기·논리 비약이 있는 경우, 정답임을 먼저 인정한 뒤 개선점을 제시한다. | P1 |
| DIAG-7 | 학생이 적용한 **해법(method)** 을 식별하여 기록한다. | P0 |

## 4. AI가 무엇을 어떻게 학습해야 하는가

가장 중요한 전제부터 말씀드립니다. **대규모 파인튜닝이나 자체 모델 학습은 MVP에 필요하지 않습니다.** 필요한 것은 세 개의 계층입니다.

```
Layer 3   운영 데이터 축적 루프      ← 서비스가 돌면서 자동으로 쌓임
   ↑
Layer 2   런타임 추론 파이프라인      ← LLM + 수식 검증기 조합
   ↑
Layer 1   지식 자산 (수작업 구축)     ← 소규모·고밀도. 여기가 진짜 자산
```

### 4.1 Layer 1 — 지식 자산 (사람이 구축하는 부분)

#### (1) 해법 카탈로그 (Method Catalog) — 최우선 자산

단원별로 **"이 유형에 적용 가능한 해법들"** 을 정리합니다. 문제를 모으는 것이 아니라 **푸는 방법을 모으는 것**입니다.

예시 — "이차함수의 최대·최소" 단원:

```json
{
  "unit": "이차함수 > 최대·최소",
  "methods": [
    {
      "id": "QF-MAX-001",
      "name": "완전제곱식 변형",
      "grade_min": "M3",
      "description": "y = a(x-p)² + q 꼴로 변형하여 꼭짓점에서 최대·최소를 읽는다",
      "applicable_conditions": ["정의역 제한 없음 또는 꼭짓점 포함"],
      "pros": "계산이 단순하고 중3 범위에서 가능",
      "cons": "정의역이 제한되면 별도 검토 필요",
      "signature_patterns": [
        "x² 계수로 묶는 변형이 나타남",
        "(x - p)² 형태의 항이 등장",
        "상수항 조정 흔적"
      ]
    },
    {
      "id": "QF-MAX-002",
      "name": "그래프 대칭축 이용",
      "grade_min": "M3",
      "description": "x = -b/2a 로 축을 구한 뒤 정의역과의 위치 관계로 판정",
      "applicable_conditions": ["정의역이 제한된 경우 특히 유효"],
      "signature_patterns": ["-b/2a 계산이 등장", "축과 구간의 대소 비교"]
    },
    {
      "id": "QF-MAX-003",
      "name": "미분 이용",
      "grade_min": "H2",
      "description": "도함수의 부호 변화로 극값 판정",
      "applicable_conditions": ["고2 미적분 이수"],
      "pros": "고차함수로 일반화 가능",
      "cons": "고1 이하 범위 밖"
    }
  ]
}
```

`signature_patterns`가 핵심입니다. 이것이 **"학생이 어떤 방법을 쓰려던 것인지"** 를 판별하는 근거가 됩니다.

**구축 규모 감각**: MVP 범위를 고1 대수·함수 영역으로 한정하면 **단원 15~20개 × 해법 5~8개 = 약 100~150건**입니다. 수학 교사 1~2명이 4~6주면 초안을 완성할 수 있는 규모이며, 기존 8단계 계획 대비 공수가 한 자릿수 배 작습니다.

#### (2) 개념 그래프 (Concept Graph)

막힌 지점을 **개념 노드**로 매핑하고, 그 개념의 **선수 개념**을 역추적하기 위한 자산입니다. "판별식에서 막혔다" → "판별식 ← 이차방정식의 근 ← 인수분해·근의 공식" 경로를 따라가면, 진짜 결손이 어디인지 짚을 수 있습니다.

노드 구조: `개념명 / 정의 / 학년 / 선수개념 ID 배열 / 대표 오개념`

2022 개정 교육과정 성취기준을 뼈대로 삼되, **선수 관계(prerequisite edge)** 를 추가하는 것이 기존 교육과정 DB와의 결정적 차이입니다. 규모는 중1~고3 전체 기준 약 400~600 노드이며, MVP는 고1 범위 100노드 내외로 시작합니다.

#### (3) 오류 유형 분류표 (Error Taxonomy)

진단 결과를 일관된 언어로 표현하고, 통계로 축적하기 위한 자산입니다.

| 대분류 | 코드 예시 | 세부 유형 |
|---|---|---|
| 계산 오류 | CALC-01~ | 사칙연산 실수, 부호 오류, 약분 오류, 지수 법칙 오적용 |
| 대수 변형 오류 | ALG-01~ | 이항 시 부호 누락, 양변 나눗셈 시 0 검토 누락, 제곱 시 부호 손실 |
| 공식 오적용 | FORM-01~ | 조건 미확인 적용, 유사 공식 혼동, 공식 암기 오류 |
| 조건 누락 | COND-01~ | 정의역 무시, 판별식 조건 누락, 실수 조건 누락 |
| 개념 오해 | CONC-01~ | 정의 오해, 필요조건·충분조건 혼동, 함수와 방정식 혼동 |
| 논리 비약 | LOGIC-01~ | 근거 없는 단정, 역·이·대우 혼동, 경우의 수 누락 |
| 표기 오류 | NOT-01~ | 등호 오용, 단위 누락, 변수 혼용 |
| 전략 부재 | STRAT-01~ | 접근 방향을 못 정함, 잘못된 해법 선택 |

각 코드에는 **피드백 템플릿**(학생에게 보여 줄 설명 문구의 뼈대)과 **관련 개념 노드**를 연결합니다. MVP 기준 **40~60개 코드**면 충분합니다.

> 참고: 수학교육학 연구에서 오류 분류 체계는 이미 여러 형태로 존재합니다. 새로 만드는 것이 아니라 **기존 분류를 서비스 피드백에 맞게 재편집**하는 작업으로 접근하면 공수가 크게 줄어듭니다.

### 4.2 Layer 2 — 런타임 추론 파이프라인

LLM 단독으로 "이 풀이가 맞나요"를 묻는 방식은 신뢰도가 낮습니다. **기호 연산 엔진(CAS)으로 검증하고, LLM은 해석과 설명을 담당하는 역할 분담**이 핵심입니다.

```
Step A  줄 단위 인식        필기/사진 → 줄 분할 → 줄별 LaTeX + 의미 태그
                            (Vision LLM. 줄 경계 인식이 관건)
   ↓
Step B  줄별 기호화          LaTeX → SymPy 표현식으로 파싱
   ↓
Step C  단계 검증 ★핵심      "n번째 줄 → n+1번째 줄 변형이 수학적으로 타당한가"를
                            CAS 동치성 검사로 판정. LLM 판단이 아닌 계산으로 확정
   ↓
Step D  이탈 지점 판정       최초 부적합 줄(오류형) 또는 마지막 줄(중단형) 결정
   ↓
Step E  해법 식별            학생 풀이 패턴 ↔ method_catalog.signature_patterns 매칭
                            (규칙 매칭 1차 + LLM 분류 2차)
   ↓
Step F  오류 유형 분류        이탈 지점의 변형 내용 ↔ error_taxonomy 매칭 (LLM)
   ↓
Step G  생성 + 자기검증       이어풀기/대안해법 생성 → 생성된 풀이를 다시 CAS로 검사
                            → 최종 답 대조 → 통과한 것만 학생에게 표시
```

**Step C가 이 서비스의 기술적 심장입니다.** 예를 들어 학생이 이렇게 썼다고 하겠습니다.

```
1행: x² - 4x + 3 > 0
2행: (x-1)(x-3) > 0
3행: x > 1 또는 x > 3        ← 오류
```

CAS는 1행↔2행이 항등적으로 동치임을 확인하고, 2행에서 3행으로의 변형이 해집합을 보존하지 않음을 계산으로 확정합니다. LLM은 그 다음에 **"왜 그런 실수를 했는지"** 를 해석하여 `COND-xx: 부등식 해집합 판정 오류`로 분류하고, 학생 언어로 설명합니다. 판정은 계산이, 설명은 LLM이 담당하는 구조입니다.

**CAS 적용 가능 범위**: 대수식·방정식·부등식·함수·수열·미적분 계산은 SymPy로 대부분 검증됩니다. **기하 증명·논증형 서술은 검증이 어렵습니다.** 따라서 MVP 범위를 **대수·함수·미적분 계산 영역**으로 한정하고, 기하·증명은 v1.2 이후로 미루는 것을 권장합니다. 이 범위 제한은 PRD 10장(Out of Scope)에 명시합니다.

**프롬프트 체계**: 시스템 프롬프트를 단일 소스로 두던 기존 8.1을 **역할별 프롬프트 4종**으로 분리합니다.

| 프롬프트 | 역할 | 주입되는 컨텍스트 |
|---|---|---|
| `P-RECOGNIZE` | 문제·풀이 줄 단위 인식 | 학년, 단원 후보 |
| `P-DIAGNOSE` | 오류 해석 및 유형 분류 | CAS 검증 결과, 오류 분류표, 개념 그래프 |
| `P-RESUME` | 학생 해법 유지 이어풀기 | 학생의 마지막 유효 줄, 식별된 해법 정의 |
| `P-ALTERNATIVE` | 대안 해법 풀이 | 선택된 해법 정의, 학년 범위 제약 |

### 4.3 Layer 3 — 운영 데이터 축적 및 개선 루프

서비스가 돌아가는 것만으로 다음 데이터가 쌓입니다.

```
학생 풀이 원본(필기 이미지 + 줄 단위 LaTeX)
  + AI 진단 결과 (막힌 지점, 오류 유형, 식별 해법)
  + 학생 반응 ("이해했어요" / "아직 모르겠어요" / 후속 질문 내용)
  + 재시도 결과 (같은 개념 문제를 다시 맞혔는가)
```

이 데이터가 만들어 내는 것은 다음과 같습니다.

| 축적량 | 가능해지는 것 |
|---|---|
| 1천 건 | 오류 유형 빈도 통계, 프롬프트 few-shot 예시 확보 |
| 5천 건 | 개념별 취약 지도, 오답 노트·학부모 리포트 실용화 |
| 1만 건 | 진단 전용 소형 모델(SLM) 파인튜닝 데이터셋 확보 |
| 3만 건 이상 | 오류 유형 기반 유사 문제 추천, 개인화 학습 경로 |

**초기 라벨링 전략**: 서비스 초기 3~6개월간 수학 교사(파트타임)가 하루 30~50건씩 AI 진단 결과를 검수합니다. 검수 결과는 ① 프롬프트 few-shot 예시 ② 평가용 골든셋 ③ 향후 파인튜닝 데이터의 세 가지로 동시에 사용됩니다. 이 검수 비용은 **지원사업 예산의 인건비 항목으로 명확히 정당화되는 지출**입니다.

### 4.4 평가 체계 — 지원사업 서술의 핵심

기술 신뢰성을 증명하려면 정량 평가 체계가 필요합니다.

**골든셋 구축**: 실제 학생 풀이 300~500건에 수학 교사가 정답 라벨(막힌 줄 번호 / 오류 유형 / 적용 해법)을 부착합니다.

| 평가 지표 | 측정 방법 | MVP 목표 |
|---|---|---|
| 줄 단위 인식 정확도 | 교사 전사본 대비 LaTeX 일치율 | 90% 이상 |
| 막힌 지점 검출 정확도 | 줄 번호 Top-1 일치율 | 85% 이상 |
| 오류 유형 분류 F1 | 대분류 기준 macro-F1 | 0.75 이상 |
| 해법 식별 정확도 | 카탈로그 ID 일치율 | 80% 이상 |
| 생성 풀이 정합성 | CAS 검증 통과율 | 98% 이상 |
| 학년 범위 준수율 | 상위 학년 개념 무단 사용 비율 | 2% 이하 |

이 표는 지원사업 신청서의 **"기술개발 목표 및 정량적 성과지표"** 항목에 그대로 쓸 수 있는 형태로 설계했습니다.

## 5. 신 구축 로드맵 — 기존 8단계의 대체안

```
STEP 1   개념 그래프 구축              2022 개정 교육과정 + 선수관계 엣지
            ↓                          (MVP: 고1 범위 100노드)
STEP 2   해법 카탈로그 구축 ★핵심       단원별 적용 가능 해법 + 시그니처 패턴
            ↓                          (MVP: 100~150건)
STEP 3   오류 유형 분류표 + 피드백 템플릿  (MVP: 40~60 코드)
            ↓
STEP 4   줄 단위 필기 인식 파이프라인    Vision 모델 + 줄 분할 + 신뢰도 표시 UI
            ↓
STEP 5   CAS 기반 단계 검증기 ★핵심      SymPy 동치성 검사 엔진
            ↓
STEP 6   진단 → 이어풀기/대안해법 생성   프롬프트 체인 4종 + 자기검증
            ↓
STEP 7   골든셋 평가 + 품질 게이트       300~500건 교사 라벨, 지표 미달 시 출시 보류
            ↓
STEP 8   운영 데이터 축적 → 진단 정밀화   여기서 문제 DB·유사문제 라인이 재진입
```

**기존 8단계와의 대응 관계**:

| 기존 | 신규 | 비고 |
|---|---|---|
| STEP 1 (교육과정 DB) | STEP 1 | **재사용**. 선수관계 엣지만 추가 |
| STEP 2~3 (평가원 예시·기출 매핑) | — | **후순위 이관**. 유사문제 추천 시점에 재개 |
| STEP 4 (Problem Family DB) | — | **후순위 이관** |
| STEP 5 (난이도 모델) | — | **후순위 이관** |
| STEP 6 (생성 템플릿) | — | **후순위 이관** |
| STEP 7 (자동 검증·품질 필터) | STEP 5 | **성격 전환 후 재사용**. 문제 검증용 CAS를 풀이 검증용으로 먼저 만들고, 나중에 문제 생성 검증에 그대로 재활용 |
| STEP 8 (학생 데이터 보정) | STEP 8 | **강화**. 보정 대상이 문제 적중률에서 진단 정확도로 바뀜 |

### 5.1 축소된 문제 DB 라인의 처리 원칙

| 자산 | 처리 |
|---|---|
| 2022 교육과정 범위 DB | **유지**. 개념 그래프의 뼈대로 승격 |
| 개념 태그 체계 | **유지**. 마이페이지 분류에 그대로 사용 |
| 평가원 예시문항 분석 | **최소 유지**. 해법 카탈로그 작성 시 "실제로 어떤 해법이 요구되는가"의 참고 자료로만 활용 |
| 기출 매핑 / Problem Family DB | **중단**. v1.2 유사문제 기능 착수 시 재개 |
| 난이도 모델 | **중단**. 진단 데이터가 쌓이면 "학생 체감 난이도"라는 더 나은 지표로 대체 가능 |
| 문제 생성 템플릿 | **중단**. v1.3 이후 |
| 자동 수학 검증 필터 | **성격 전환하여 최우선 착수**. 풀이 검증기로 먼저 구현 |

투자 낭비를 최소화하는 지점은 두 곳입니다. **교육과정 DB**와 **수학 검증기**는 어느 방향으로 가든 필요한 자산이며, 이미 투입한 공수가 그대로 살아납니다.

## 7. 지원사업 신청서 서술 관점

이번 전환은 지원사업 관점에서도 서술이 유리해집니다.

**기술 차별성** — 기존 수학 학습 서비스는 "문제를 인식하여 정답 풀이를 제공"하는 단계에 머물러 있습니다. 본 서비스는 **학생이 작성한 풀이 과정을 줄 단위로 분해하고 기호 연산 엔진으로 검증하여, 오류가 발생한 정확한 지점과 원인을 판정**하는 기술을 구현합니다. 이는 국내 상용 서비스에서 구현 사례를 찾기 어려운 영역입니다.

**기술 구현 방식의 신뢰성** — 대규모 언어모델의 판단에만 의존하지 않고, **기호 연산 기반 수학적 검증을 판정의 근거로 삼고 언어모델은 해석과 설명을 담당**하는 이중 구조를 채택합니다. 이를 통해 생성형 AI의 환각 문제를 구조적으로 통제합니다.

**데이터 자산 확보** — 학생의 실제 풀이 과정과 오류 패턴 데이터는 기존 문제은행에 존재하지 않는 신규 데이터입니다. 서비스 운영이 곧 데이터 축적으로 이어지는 구조를 설계하여, 시간이 지날수록 진단 정확도가 향상되는 선순환을 확보합니다.

**정량적 성과지표** — 4.4절의 평가 지표표를 기술개발 목표로 그대로 제시할 수 있으며, 골든셋 기반 측정 방법까지 명시되어 있어 검증 가능성이 높습니다.

**사업화 경로** — 1단계 학생 대상 B2C, 2단계 학부모 리포트를 통한 구독 전환, 3단계 축적된 오류 데이터 기반 교사·학원 대상 B2B 진단 리포트로 확장하는 단계적 수익 모델을 제시할 수 있습니다.
