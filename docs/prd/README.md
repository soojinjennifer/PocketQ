# PRD 계층 구조

포켓큐(수풀잉)의 제품 요구사항은 두 단계로 관리한다.

```
Level 0  docs/PRD_WHYMATH.md            제품 전체 PRD (최고 우선순위)
  │        §4.x 요구사항 ID + 핵심 수용 기준
  │        §11  하위 PRD 목록
  │
  └─ Level 1  docs/prd/L1_<영역>.md      영역별 상세 PRD
               정책 수치, 화면 문구, 상태 전이, 데이터 모델, 외부 연동, QA 시나리오
```

## 1. 우선순위와 충돌 처리

1. **L0가 L1보다 우선한다.** L1은 L0의 결정을 바꾸지 않고 구체화만 한다.
2. L1이 L0와 다르게 쓰여 있으면 L0를 따르고, 차이를 해당 L1의 "미결정 사항"에 올린다. 오너가 결정하면 L0와 L1을 같은 커밋에서 함께 고친다.
3. 다른 문서(`docs/*.md` 설계·상태 문서, `references/`)는 L0·L1보다 우선하지 않는다. `CLAUDE.md`의 기술 스택·폴더 규칙은 L0 §6.1과 같으며, L1이 이를 바꿀 수 없다.
4. 기존 코드·마이그레이션이 L1과 다르면 코드를 바로 고치지 않는다. plan-agent가 차이를 보고하고 오너가 어느 쪽을 따를지 정한다.

## 2. 요구사항 ID

- ID는 **L0에서 정의한다.** (예: L0 §4.13의 `BILL-1` ~ `BILL-12`)
- L1은 문서 앞에 "요구사항 ID ↔ 상세 섹션" 표를 두어 각 ID가 어느 섹션에서 상세화되는지 밝힌다.
- 추적성 검증(stage-qa-agent, final-qa-agent)은 L0의 ID 목록을 기준으로 하고, 수용 기준 세부는 L1을 참조한다.
- L1에서 새 요구사항이 필요해지면 먼저 L0에 ID를 추가한다. L1에만 있는 ID는 만들지 않는다.

## 3. L1 문서 형식

| 필수 항목 | 내용 |
|---|---|
| 머리 표 | PRD 레벨, 상위 PRD와 섹션, 요구사항 ID 접두어, 상태, 버전, 작성일 |
| §0 ID 매핑 | L0 ID ↔ L1 상세 섹션 |
| 범위 | 목표, 하지 않는 것 |
| 상세 명세 | 정책, 화면 흐름, 상태 전이, 데이터, API, 외부 연동 |
| 완료 기준 | 단계별 체크리스트, 출시 기준 |
| 미결정 사항 | 질문, 기본안, 결정 주체 |

상태 값: `초안` → `plan-agent 검증 완료` → `오너 승인` → `구현 중` → `완료`

## 4. 새 L1 추가 절차

1. `docs/prd/L1_<영역>.md`를 위 형식으로 작성한다.
2. L0에 해당 영역 섹션(§4.x)을 만들고 ID와 핵심 수용 기준, L1 링크를 넣는다.
3. L0 §11 하위 PRD 목록과 머리말 변경 이력에 추가한다.
4. plan-agent가 L0·L1·현재 코드를 대조해 검증하고, 결과를 L1의 미결정 사항과 상태에 반영한다.
