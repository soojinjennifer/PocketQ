## 1. 배경과 목표

### 1.1 배경
수풀잉은 현재 무료로 운영하고 있다. 오픈 무료 운영 기간이 끝난 뒤 월 정액 구독(Basic)으로 전환한다. 카드는 가입할 때 받지 않고 **체험이 끝난 뒤 사용자가 직접 구독을 시작할 때** 받는다. 그래서 체험이 끝나도 자동으로 결제되지 않는다.

### 1.2 핵심 구조
> **7일 무료 체험 → 체험 종료 → 사용자가 카드 등록·정기결제에 동의하고 첫 결제 → 이후 매월 13,900원 자동결제**

### 1.3 목표
- G1. 무료 운영 → 체험 → 유료 전환까지 사용자가 헷갈리지 않고 이해할 수 있는 흐름을 만든다.
- G2. 첫 결제, 다음 달 갱신, 해지, 실패 복구가 **중복 청구나 누락 없이** 동작한다.
- G3. 이용 권한은 언제나 서버가 판정한다. 화면을 우회해도 무료 이용·구독 상태를 벗어날 수 없다.

### 1.4 이번 범위에서 하지 않는 것 (Non-goals)
- 연간 요금제, 쿠폰, 프로모션 코드, 가족·기관 요금제
- 카드 외 결제수단(간편결제, 계좌이체, 휴대폰 결제)
- 갱신 실패 시 자동 재시도(초기에는 사용자가 직접 재시도)
- AI 사용량 무제한 정책. **월 정액과 무제한 사용은 별도 정책이다.** 현재 사용 한도를 유지하고, Basic 제공량은 `plans.usage_limits`에 명시한다.
- 앱스토어 인앱결제(iOS/Android 네이티브 앱 결제)

## 3. 요금·이용 정책

### 3.1 요금표

| 구분 | 요금 | 이용 기간·전환 방식 |
|---|---|---|
| 오픈 무료 운영 | 무료 | 11월 2일~11월 30일, 카드 등록 없이 이용 |
| Free 체험 | 무료 | 계정당 최초 7일, 카드 등록 없이 이용 |
| Basic | 월 13,900원 | 체험 종료 후 직접 구독 시작, 이후 매월 자동결제 |
| 체험 종료·미결제 | 무료 이용 종료 | 기존 기록 열람 가능. 새 AI 풀이·후속 질문 제한 |

- 13,900원은 사용자가 실제로 내는 **최종 금액**이다. 과세 구분(과세/면세)과 부가세 표기는 사업자 설정을 따른다 → [미결정 사항 Q3](#11-미결정-사항-오픈-이슈).
- 가격은 `plans` 테이블에서 서버가 결정한다. 브라우저가 보낸 금액은 절대 그대로 청구하지 않는다.

### 3.2 무료 이용 종료일 계산 규칙

```
trial_end         = trial_started_at + 7일   (v1.1 시행 전 가입자만 30일, §3.3)
open_promo_end    = 2026-12-01 00:00 KST   (billing_settings.open_promo_end_at)
free_access_end   = max(trial_end, open_promo_end)
```

- 체험은 **가입 시점에 시작**한다(오픈 무료 운영 기간에 가입해도 체험 시계는 그때부터 돈다).
- 무료 운영이 끝난 뒤 모든 사용자에게 7일을 다시 주지 않는다.
- 체험은 계정당 1회다. 탈퇴 후 재가입으로 체험을 다시 받는 것을 막을 방법은 [Q5](#11-미결정-사항-오픈-이슈)에서 정한다.

#### 예시 (기준 테스트 케이스로 사용)

| # | 가입 시각(KST) | trial_end | free_access_end | 이유 |
|---|---|---|---|---|
| E1 | 11/02 10:00 | 11/09 10:00 | **12/01 00:00** | 무료 운영 종료가 더 늦음 |
| E2 | 11/25 15:00 | 12/02 15:00 | **12/02 15:00** | 체험이 무료 운영보다 15시간 더 김 |
| E3 | 11/28 15:00 | 12/05 15:00 | **12/05 15:00** | 체험이 더 늦음 |
| E4 | 12/01 15:00 | 12/08 15:00 | **12/08 15:00** | 유료 운영 기간 가입, 7일 체험 |
| E5 | 기존 회원(10/26 이전 가입, 예: 10/01) | 10/31 (가입 + 30일, 경과 조치) | **12/01 00:00** | 무료 운영 기간 보장 후 구독 안내 |
| E6 | 10/27 12:00 (약관 v1.0 가입) | 11/26 12:00 (경과 조치 30일) | **12/01 00:00** | 30일 체험이어도 무료 운영 종료가 더 늦음 |
| E7a | 10/28 23:59:59 | 11/27 23:59:59 (30일) | **12/01 00:00** | 약관 v1.1 시행 직전 가입 → 30일 |
| E7b | 10/29 00:00:00 | 11/05 00:00 (7일) | **12/01 00:00** | 약관 v1.1 시행 시각 가입 → 7일 |

### 3.3 기존 체험 정책 이전
- **결정(2026-10-28): 무료 체험은 가입 후 7일이다.** 이를 위해 이용약관을 v1.1로 개정했다(`apps/web/public/terms.html` 제6조, 시행 2026-10-29). v1.0(2026-10-26 시행)은 "가입하면 30일 동안 무료 체험"이었다.
- **경과 조치:** v1.1 시행 전(2026-10-29 00:00 KST 전) 가입자는 v1.0에 동의했으므로 가입 + 30일을 유지한다(약관 부칙). 해당 가입자는 10/26~10/28 3일간의 가입자이고, 30일 체험이 늦어도 11/27에 끝나 오픈 무료 운영(제안 11/30까지) 안에 들어가므로 **실제로 무료 기간이 늘어나는 사용자는 없다.** 동의한 조건을 고지 없이 줄이는 위험(약관 제3조의 불리한 변경 30일 전 고지)만 없앤다.
- v1.1 시행 이후 가입자는 v1.1에 동의하고 가입하므로 별도 고지 기간 없이 7일이 적용된다.
- 기준 시각은 `billing_settings.trial_7d_effective_at = 2026-10-29 00:00 KST`에 둔다. 가입 트리거는 가입 시각이 이 값 이후면 7일, 이전이면 30일로 정한다. 실제 배포일이 다르면 약관 시행일·이 값·`CONSENT_POLICY_VERSION`을 같은 날짜로 맞춘다.
- 코드의 15일(`profiles.sql` 트리거, DB 미적용 추정)은 이용자에게 알린 적이 없는 값이므로 쓰지 않는다.
- 이미 약속한 만료일은 줄이지 않는다.
- 체험 정보는 기존 서버 전용 `profiles` 테이블(`supabase/migrations/20260909000000_profiles.sql`)을 확장해 보관한다(§7.1). 별도 `user_trials` 테이블은 만들지 않는다.
- 가입 트리거 `handle_new_user`의 `interval '15 days'`를 `billing_settings.trial_days`(7) 기준으로 바꾼다.
- 백필: v1.1 시행 전 가입자는 `trial_ends_at = greatest(기존 trial_ends_at, created_at + 30일)`, `trial_source = 'terms_v1_30d'`. 시행 이후 가입자는 `created_at + 7일`, `trial_source = 'signup_7d'`. 모두 `trial_started_at = auth.users.created_at`. 15일 값이 들어 있는 행이 있어도 늘어나기만 하고 줄지 않는다. 마이그레이션 전후로 만료일이 줄어든 사용자 수가 0명인지 검증한다.
- 운영 DB에 `profiles`가 적용됐는지는 Q15에서 확인한다. 적용되지 않았다면 모든 기존 회원이 E5에 해당한다.

### 3.4 이용 권한(Entitlement) 상태

서버가 요청마다 아래 순서로 판정한다.

| 우선순위 | 상태 | 조건 | 새 AI 풀이·후속 질문 | 기존 기록 열람 |
|---|---|---|---|---|
| 1 | `basic_active` | `subscriptions.status IN ('active','cancel_scheduled','past_due') AND now < current_period_end`. `incomplete`·`expired`·`refunded`는 기간이 남아 있어도 해당하지 않는다 | 허용 (Basic 한도) | 허용 |
| 2 | `open_promo` | `open_promo_start_at <= now < open_promo_end_at`, 또는 `paid_mode_enabled = false` | 허용 (현재 무료 한도) | 허용 |
| 3 | `trial` | `now < trial_end` | 허용 (현재 무료 한도) | 허용 |
| 4 | `expired` | 위 조건 모두 아님 | **차단** (402, `{ error: { code: "subscription_required", message } }`) | 허용 |

- `paid_mode_enabled`는 유료 전환 스위치다. `false`이면 기간과 관계없이 모든 사용자를 `open_promo`로 판정한다(긴급 시 유료 전환을 끄는 용도). 날짜에 따른 전환은 `open_promo_end_at`으로만 한다.
- `open_promo_start_at` 이전 시각은 운영상 발생하지 않지만, 이 경우에도 `open_promo`가 아니라 `trial`/`expired` 규칙을 따른다.
- 오류 코드는 기존 규약(`packages/shared-types/src/index.ts` `ErrorCode`, `docs/API_SPEC.md`의 소문자 snake_case)에 `"subscription_required"`를 추가해 쓴다.
- 판정 함수는 하나(`getEntitlement(userId, now)`)로 두고, 아래 AI 호출 라우트가 모두 `requireEntitlement` 미들웨어로 이 함수를 거친다.

| 라우트 (현재 코드) | 근거 | 판정 |
|---|---|---|
| `POST /api/problems/recognize` | `modules/recognition/recognition.router.ts` | 차단 대상 |
| `POST /api/problems/:problemId/work-lines` | `modules/work/work.router.ts` | 차단 대상 |
| `POST /api/problems/:problemId/diagnose` | `modules/diagnosis/diagnosis.router.ts` | 차단 대상 |
| `POST /api/problems/:problemId/solve` (SSE) | `modules/solutions/solutions.router.ts` | 차단 대상 |
| `POST /api/problems/:problemId/resume` (SSE) | `modules/resume/resume.router.ts` | 차단 대상 |
| `POST /api/problems/:problemId/chat` | `modules/chat/chat.router.ts` | 차단 대상 |
| `POST /api/problems/:problemId/suggestions` | `modules/suggestions/suggestions.router.ts` | 차단 대상 |
| `GET /api/problems`, `GET /api/problems/:problemId`, `POST /api/problems/:problemId/reopen` | `modules/problems/problems.router.ts` | 허용 (AI를 호출하지 않는 기록 열람) |
| `POST /api/problems/bulk-delete`, `DELETE /api/account/unconsented` | `problems.router.ts`, `account.router.ts` | 허용 (본인 데이터 삭제) |

- 미들웨어 순서는 `authenticate` → `requireEntitlement` → `rateLimiter` → 검증·핸들러다. SSE 라우트(solve, resume)는 응답 헤더를 보내기 전에 402를 반환해야 한다.
- 새 AI 호출 라우트를 추가하면 이 표에 넣고 같은 미들웨어를 붙인다.
- 화면용 상태 API(`GET /api/billing/status`)도 같은 함수 결과를 쓴다. 화면과 API의 판정이 달라지면 안 된다.
- 이용 기간 경계는 반열린 구간 `[start, end)`로 통일한다. `end` 시각 정각에는 이미 만료다.

| 오픈 무료 운영 중 | "오픈 기념 무료 이용 중 · {M월 D일}까지" | 문제 풀기 |

| 체험 종료 | "무료 체험이 종료되었어요. Basic으로 학습을 이어가세요." | 월 13,900원으로 시작하기 |
| 구독 신청 | 오늘 결제금액, 매월 결제금액, 다음 결제일, 해지·환불 안내 | 동의하고 카드 등록·결제하기 |
| 결제 처리 중 | "결제를 확인하고 있어요" (버튼 비활성) | — |
| 결제 성공 | "Basic 구독이 시작되었어요" | 문제 풀기 |
| 결제 실패 | 실패 사유와 재시도 안내 | 결제 다시 시도 |
| 갱신 실패·만료 | "결제가 완료되지 않아 Basic 이용이 멈췄어요. 카드를 확인해 주세요." | 카드 변경 후 결제하기 |

- 화면의 모든 날짜는 서버(`GET /api/billing/status`)가 `billing_settings`와 `profiles` 값으로 만들어 내려준다. 화면 코드에 "11월 15일" 같은 날짜를 고정으로 쓰지 않는다(무료 운영 연장 시 설정값만 바꾼다).
- 오픈 무료 운영 문구의 `{M월 D일}`은 `open_promo_end_at - 1초`의 KST 날짜다(기본값 11월 30일).
- 남은 기간 문구는 **KST 달력 날짜** 기준이다. `D = (free_access_end - 1초 의 KST 날짜) - (now의 KST 날짜)`
  - `D = 0` → "무료 체험이 오늘 HH:MM에 끝나요"
  - `D = 1` → "무료 체험이 내일 HH:MM에 끝나요"
  - `D ≥ 2` → "무료 체험이 D일 남았어요"
  - `free_access_end`가 00:00 정각이면 시각을 "00:00" 대신 "자정"으로 표기한다(예: 11/20 00:00 종료를 11/19에 보면 "오늘 자정에 끝나요").
- 권한 판정(§3.4 우선순위)과 문구 기준은 다를 수 있다. 예: E2는 11/30에 판정은 `open_promo`지만 문구는 더 늦게 끝나는 체험 기준이다.
- 무료 운영과 체험이 겹치면 `free_access_end`를 만든 쪽의 문구를 쓴다. 무료 운영 종료가 더 늦으면 무료 운영 문구, 체험 종료가 더 늦으면 체험 문구다.

### 4.2 구독 신청 화면 필수 고지 (결제 전 표시)

> 오늘 **13,900원**이 결제되며, 이후 매월 **{결제 기준일}일**에 등록한 카드로 자동결제됩니다.
> 다음 결제일: **{YYYY년 M월 D일}**
> 다음 결제일 전에 구독을 해지하면 이후 결제는 진행되지 않습니다.
> 환불 기준: {확정된 환불 정책 요약 + 링크}

- 동의 체크박스: ① 정기결제(자동결제) 동의 ② 이용약관·환불정책 동의. 둘 다 체크해야 버튼이 켜진다. 미리 체크해 두지 않는다.
- 만 19세 미만 학생은 이 화면에 오기 전에 보호자 동의(§4.5)를 받아야 한다. 보호자 동의가 유효하지 않으면 "동의하고 카드 등록·결제하기" 버튼 대신 "보호자 동의 요청하기"를 보여준다.
- 동의 시각, 약관 버전, 화면에 보여준 금액·주기를 `subscription_consents`에 저장한다.
- 다음 결제일 문구는 서버가 계산해 내려준다(월말 규칙 반영, 5.2).

### 4.3 결제 성공 판정
- **카드 등록 성공 ≠ 결제 성공.** 첫 결제가 승인(`DONE`)되어야 Basic 권한을 준다.
- 카드 등록은 됐는데 첫 결제가 실패하면: 빌링키는 보관하되 구독은 `incomplete`로 두고, "결제 다시 시도" 버튼으로 같은 카드에 재결제하거나 카드를 바꿀 수 있게 한다.

### 4.4 마이페이지 > 구독 관리

| 항목 | 내용 |
|---|---|
| 현재 플랜 | 오픈 무료 / 무료 체험 / Basic / Basic(해지 예약) / 이용 종료 |
| 날짜 | 무료 이용 종료일 **또는** 다음 결제일. 해지 예약 상태면 "M월 D일까지 이용 가능" |
| 등록 카드 | 카드사 + 마스킹 번호 (예: 신한 ****1234) |
| 결제내역 | 결제일, 이용 기간, 금액, 상태(완료/실패/취소/환불), 영수증 링크 |
| 보호자 동의 | 만 19세 미만이면 동의 상태(대기·완료·거절·철회)와 동의 일시, 보호자 이름(일부 마스킹) |
| 카드 변경 | 토스 카드 등록창 재호출 → 새 빌링키로 교체 |
| 구독 해지 | 확인 모달("M월 D일까지 이용할 수 있고, 이후 결제는 진행되지 않아요") → 해지 예약 |
| 해지 취소 | 해지 예약 상태에서 이용 기간이 남아 있으면 "구독 계속하기"로 해지 취소 |


### 4.5 만 19세 미만 학생의 결제 — 학생 결제 + 보호자(법정대리인) 동의 (Q11 결정, 2026-10-28)

**결정:** 결제는 학생 계정에서 학생이 진행하고, 만 19세 미만이면 결제 전에 보호자가 결제 조건에 동의해야 한다. 약관 제6조(`apps/web/public/terms.html:62`)의 "만 19세 미만은 법정대리인의 명시적인 동의" 약속을 이행하는 절차다.

**흐름**

| 단계 | 학생 화면 | 보호자 화면 | 서버 |
|---|---|---|---|
| 1. 연령 확인 | 구독 시작 시 "만 19세 이상이에요 / 만 19세 미만이에요" 중 하나를 고른다(미리 선택 없음) | — | 자기 신고 값과 시각 저장. 19세 이상이면 §4.2로 바로 이동 |
| 2. 보호자 정보 입력 | 보호자 이름, 관계(부·모·그 밖의 법정대리인), 보호자 연락처(이메일, Q19) 입력 | — | `guardian_consents` 행 생성(`pending`), 1회용 토큰 발급(해시만 저장), 동의 요청 발송 |
| 3. 대기 | "보호자 동의를 기다리고 있어요" + 다시 보내기·정보 수정 | — | 토큰 유효 기간 7일 |
| 4. 보호자 동의 | — | 링크를 열면 결제 조건을 본다: 서비스명, 학생 닉네임과 마스킹 이메일, 플랜·월 13,900원·매월 자동결제, 해지 방법, 환불 기준, 미성년자 계약 안내. 보호자 이름 확인 후 "동의합니다" / "동의하지 않습니다" | 결과·시각·IP·UA·보여준 조건(금액·주기·약관 버전) 저장. 토큰 폐기 |
| 5. 결제 | 동의가 확인되면 §4.2 구독 신청 화면 → 카드 등록·결제 | 동의 완료 안내 | 결제 시 `subscription_consents.guardian_consent_id`로 연결 |

**규칙**
- 보호자 동의는 **플랜·가격·주기 단위**로 유효하다. 가격이나 주기가 바뀌면 다시 동의를 받는다. 같은 조건이면 해지 후 재구독할 때 다시 받지 않는다.
- 카드는 학생 본인 카드와 보호자 카드 모두 쓸 수 있다. 카드 명의자 확인은 하지 않는다(토스 카드 등록창의 카드사 인증에 맡긴다).
- 보호자가 "동의하지 않습니다"를 고르거나 링크가 만료되면 학생은 결제할 수 없고 무료 이용 종료 후 `expired` 상태가 된다. 학생은 동의를 다시 요청할 수 있다.
- 보호자는 동의 완료 안내에 있는 링크로 언제든 동의를 철회할 수 있다. 철회하면 구독을 해지 예약(`cancel_scheduled`)으로 바꾸고, 이미 결제한 기간은 끝까지 이용한다.
- 보호자 동의를 받고 맺은 계약은 미성년자라는 이유로 취소할 수 없다는 점(민법 제5조)을 보호자 동의 화면에 안내한다. 동의 없이 결제가 이뤄지는 경로가 없어야 한다.
- 19세 이상 자기 신고가 사실과 다를 수 있다. 신고 값과 시각을 남기고, 보호자가 미동의 결제를 알려오면 환불 정책(Q2)에 따라 처리한다.
- 보호자 연락처는 동의 요청·동의 기록·철회 안내에만 쓴다. 마케팅이나 다른 안내에 쓰지 않는다.
- 보호자 동의 화면은 로그인 없이 토큰으로 연다. 토큰은 추측할 수 없는 값(128비트 이상)으로 만들고, URL 경로에 넣되 보호자·학생 개인정보는 URL에 넣지 않는다.

## 5. 결제·구독 정책

### 5.1 처리 규칙

| 항목 | 규칙 |
|---|---|
| 첫 결제 | 체험 종료 후 사용자가 구독을 시작한 시점에 즉시 13,900원 |
| 체험 중 구독 | **[Q1]** 체험 중에도 구독 시작을 허용할지 결정 필요. 허용한다면 기본안: 즉시 결제, 남은 체험 기간은 소멸 |
| 다음 결제 | 첫 결제일 기준 매월 같은 날짜(결제일). 결제일 03:00 KST에 시도하고, 이용 기간은 결제일 다음 날 00:00에 끝난다. 즉 **이용 기간이 끝나기 하루 전에 결제를 시도한다** (Q13 결정, §5.2) |
| 월말 결제 | 해당 날짜가 없는 달은 말일에 결제하고, 그다음 달은 원래 기준일로 복원 |
| 늦게 구독 시작 | 체험 종료 후 지난 기간은 청구하지 않는다. 구독 시작일이 새 기준일이 된다 |
| 구독 해지 | 즉시 다음 자동결제를 중단(해지 예약). 이미 결제한 이용 기간 끝까지 사용. 화면 안내는 "결제일 전날까지 해지하면 다음 결제가 진행되지 않아요". 서버는 결제 시도 직전까지 해지를 반영한다(§6.3) |
| 환불 | 해지와 별도로 처리. 확정된 환불 정책에 따라 결제 취소 및 권한 조정 **[Q2]** |
| 첫 결제 실패 | Basic을 활성화하지 않고 재시도 안내 |
| 갱신 결제 실패 | `past_due`로 바꾸고 결제일 당일(이용 기간 끝, 결제일 다음 날 00:00)까지는 Basic을 유지한다. 실패 즉시 화면에 카드 확인·변경 안내. 기간이 끝나면 새 AI 요청 제한, 기존 기록 유지 |
| 결제 재시도 | 초기에는 사용자가 직접 재시도. **기간이 끝나기 전(`past_due`)에 성공**하면 원래 기간에 이어서 다음 기간을 시작하고 기준일은 그대로 둔다. **기간이 끝난 뒤(`expired`)에 성공**하면 성공 시점부터 새 이용 기간을 시작하고 기준일을 성공일로 바꾼다 |
| 응답 유실 | 실패로 단정해 다시 청구하지 않는다. 주문번호로 결제 상태를 먼저 조회한다 (6.5) |

### 5.2 다음 결제일 계산

```
anchor_day = 첫 결제일(KST)의 day
next_billing_date(year, month) = min(anchor_day, 해당 월의 말일)
```

| 첫 결제일 | 이후 결제일 |
|---|---|
| 1월 15일 | 2/15 → 3/15 → 4/15 |
| 1월 31일 | 2/28 (윤년 2/29) → 3/31 → 4/30 → 5/31 |
| 3월 30일 | 4/30 → 5/30 → 6/30 |

**이용 기간과 결제 시도 시각 (Q4·Q9·Q13 결정, 2026-10-28: 하루 전 시도)**

```
결제일 D          = min(anchor_day, 해당 월의 말일)          (KST 날짜)
period_end        = (다음 결제일 D' + 1일) 00:00 KST          = 결제일 D'이 끝나는 시각
next_billing_at   = period_end - 1일 = D' 00:00 KST          (이 시각부터 결제 대상)
결제 시도         = D' 03:00 KST 정기 작업                     (기간 종료 21시간 전)
첫 이용 기간      = [첫 결제 시각, period_end)
갱신 이용 기간    = [직전 period_end, 다음 period_end)         (기간 사이에 빈틈 없음)
```

| 첫 결제 | 첫 이용 기간 | 갱신 시도 | 갱신 이용 기간 |
|---|---|---|---|
| 1/15 14:00 | 1/15 14:00 ~ 2/16 00:00 | 2/15 03:00 | 2/16 00:00 ~ 3/16 00:00 |
| 1/31 09:00 | 1/31 09:00 ~ 3/1 00:00 | 2/28 03:00 | 3/1 00:00 ~ 4/1 00:00 (다음 시도 3/31 03:00) |

- 화면의 "다음 결제일"과 해지 예약의 "M월 D일까지 이용 가능"은 모두 결제일 D'이다(같은 날짜). 예: 1/15 구독 → "다음 결제일 2월 15일", 해지하면 "2월 15일까지 이용 가능".
- 첫 이용 기간은 한 달보다 결제 당일의 남은 시간만큼 길다. 추가 청구는 없다.
- 결제일 03:00 시도가 실패하면 `past_due`로 두고, 그날 24:00(`period_end`)까지 Basic을 유지한다. 이 시간이 갱신 실패 유예 기간이다(별도 유예 일수는 두지 않는다).
- 정기 작업이 03:00에 돌지 못한 경우에도 `next_billing_at <= now` 조건으로 같은 날 다음 실행에서 처리한다. 결제일이 끝날 때까지 처리되지 않으면 운영 알림을 보낸다.
- 갱신 결제 실패로 만료된 뒤 사용자가 직접 재결제하면 `anchor_day`를 재결제일로 다시 정한다.

### 5.3 구독 상태 전이

```
            카드 등록 + 첫 결제 요청
 (없음) ──────────────────────────▶ incomplete
                                       │ 첫 결제 승인
                                       ▼
   ┌──────────── 갱신 승인 ────────── active ◀──── 해지 취소 ────┐
   │                                   │  │                      │
   └──────────────────────────────────▶│  └── 해지 요청 ──▶ cancel_scheduled
                                       │                         │ period_end 도달
                         갱신 결제 실패 ▼                         ▼
                                   past_due ── period_end 도달 ─▶ expired
                                       │                         ▲
                                       └── 재결제 성공 ─▶ active  │
                                  incomplete ─ 결제 미완료 방치 ──┘ (권한 없음 상태 유지)
```

| 상태 | 의미 | Basic 권한 |
|---|---|---|
| `incomplete` | 카드 등록·첫 결제 진행 중이거나 첫 결제 실패 | 없음 |
| `active` | 결제된 이용 기간 안, 다음 결제 예정 | 있음 |
| `cancel_scheduled` | 해지 예약. 다음 결제 없음 | 기간 끝까지 있음 |
| `past_due` | 갱신 결제 실패(결제일 03:00). 결제일 24:00(`period_end`)까지 이용 가능 | 기간 끝까지 |
| `expired` | 이용 기간 종료, 결제 없음 | 없음 |
| `refunded` | 환불로 권한 회수 | 없음 |

## 6. 토스페이먼츠 빌링 연동

> 자동결제(빌링)는 토스페이먼츠 **추가 검토·계약**이 필요하다. 오픈 무료 운영 기간에 계약과 테스트를 병행한다. 계약 전에도 테스트 키로 개발할 수 있다. 아래 API 경로·필드명은 구현 시 토스페이먼츠 개발자센터 최신 문서로 다시 확인한다.

### 6.1 처리 순서 (첫 구독)

```
브라우저                    수풀잉 서버                         토스페이먼츠
   │ 1. 구독 신청 화면 요청      │                                   │
   │──────────────────────────▶│ 가격·다음 결제일 계산(plans)        │
   │◀──────────────────────────│                                   │
   │ 2. 동의 + "카드 등록·결제"   │                                   │
   │──────────────────────────▶│ consent 저장, customerKey 조회/생성 │
   │◀── customerKey, success/fail URL ─│                            │
   │ 3. requestBillingAuth(카드 등록창) ───────────────────────────▶│
   │◀────────────── successUrl?authKey=...&customerKey=... ─────────│
   │ 4. authKey, customerKey 전달 │                                   │
   │──────────────────────────▶│ customerKey가 로그인 사용자 것인지 검증│
   │                           │ 5. 빌링키 발급 요청 ───────────────▶│
   │                           │◀──────── billingKey, 카드 정보 ─────│
   │                           │ 빌링키 암호화 저장                   │
   │                           │ 6. payment_order 생성(orderId)      │
   │                           │ 7. 빌링 결제 요청(13,900원) ────────▶│
   │                           │◀──────────── 승인 결과 ─────────────│
   │                           │ 8. 트랜잭션: attempt/order/subscription│
   │◀── 결과(성공/실패 사유) ────│     /이용 기간 저장                  │
```

| 단계 | API (확인 필요) | 비고 |
|---|---|---|
| 카드 등록창 | SDK v2 `payment.requestBillingAuth` (method: 카드, `customerKey` 필요) | successUrl / failUrl은 서버가 정한 고정 경로 |
| 빌링키 발급 | `POST /v1/billing/authorizations/issue` `{ authKey, customerKey }` | 시크릿 키 Basic 인증, 서버에서만 호출 |
| 빌링 결제 | `POST /v1/billing/{billingKey}` `{ customerKey, amount, orderId, orderName }` | `Idempotency-Key` 헤더에 `orderId` 기반 값 사용(최대 300자, 유효 15일 — 확인 필요). `orderId`는 6~64자 영문·숫자·`-`·`_` |
| 결제 조회 | `GET /v1/payments/orders/{orderId}` | 응답 유실·대사용 |
| 결제 취소 | `POST /v1/payments/{paymentKey}/cancel` `{ cancelReason, cancelAmount? }` | 환불용 |
| 웹훅 | 결제 상태 변경 이벤트, 빌링키 삭제 이벤트(`BILLING_DELETED`, 확인 필요) | 서명 제공 여부 확인 필요. 수신 시 조회 API로 재확인 후 반영(웹훅 본문만 믿지 않음). 빌링키 삭제 이벤트를 받으면 `billing_methods.status = 'deleted'`, 다음 갱신 전 카드 변경 안내 |

### 6.2 customerKey
- 서버가 사용자별로 **무작위 값**(UUID v4 등)을 만든다. 이메일·전화번호·user_id를 그대로 쓰지 않는다.
- 사용자당 1개를 `profiles.customer_key`에 보관하고 카드 변경 시에도 재사용한다.
- successUrl로 돌아온 `customerKey`가 로그인 사용자의 값과 다르면 즉시 거부하고 로그를 남긴다.

### 6.3 정기 결제 스케줄
- **토스페이먼츠는 매월 결제 일정을 관리하지 않는다.** 수풀잉 서버가 스케줄을 관리하고 빌링 API를 호출한다.
- 정기 작업(cron): 매일 KST 03:00(UTC 18:00) 실행. 대상은 `status = 'active' AND next_billing_at <= now AND now < current_period_end`인 구독. `next_billing_at = current_period_end - 1일`이므로 결제일 당일에 시도한다(§5.2). 실행 환경은 Q14에서 정한다.
- 결제 성공: 새 `payment_order`의 기간을 `[current_period_end, 다음 period_end)`로 저장하고, 구독의 `current_period_*`와 `next_billing_at`을 다음 기간으로 옮긴다.
- 결제 실패: 구독을 `past_due`로 바꾸고 `next_billing_at`은 그대로 둔다(같은 기간을 다시 자동 청구하지 않는다. 재시도는 사용자가 직접 한다).
- 구독마다:
  1. 행 잠금(`SELECT ... FOR UPDATE SKIP LOCKED`) 또는 advisory lock 획득
  2. 해지 예약 여부 재확인 (해지와 청구가 동시에 실행될 때를 대비)
  3. 다음 이용 기간에 대한 `payment_order`를 `(subscription_id, period_start)` 고유 제약으로 생성. 이미 있으면 재사용(새로 만들지 않음)
  4. 결제 요청 → 결과 반영
- 작업이 중간에 죽어도 다시 실행하면 같은 주문을 이어서 처리한다(멱등).

### 6.4 카드 정보 보안
- 카드번호·유효기간·CVC는 수풀잉 서버·DB·로그에 **들어오지 않는다.** 토스 등록창에서만 입력한다.
- 빌링키는 서버 전용 저장소에 **암호화**해 저장(애플리케이션 레벨 AES-GCM 또는 Supabase Vault). 키는 환경변수/시크릿 매니저로 관리.
- 빌링키·시크릿 키는 브라우저 응답, 클라이언트 로그, 에러 리포팅 도구에 절대 실리지 않게 한다(로그 마스킹).
- 화면에는 카드사명과 마스킹 번호만 보여준다.

### 6.5 응답 유실·장애 복구

| 상황 | 처리 |
|---|---|
| 결제 요청 후 타임아웃·네트워크 끊김 | attempt를 `unknown`으로 기록 → `orderId`로 결제 조회 → `DONE`이면 성공 처리, 결제 없음이면 실패 처리. **조회 전에는 재청구 금지** |
| 토스 승인 후 DB 저장 실패 | 대사(reconciliation) 작업이 `pending`/`unknown` 주문을 조회해 상태를 맞춘다 |
| 사용자가 결제 버튼 연타 | 버튼 비활성 + 서버에서 사용자별 진행 중 주문이 있으면 그 주문을 반환(새 주문 생성 안 함) |
| 브라우저가 successUrl로 두 번 돌아옴 | `authKey` 처리 결과를 저장해 두고 두 번째 요청은 같은 결과 반환 |
| 웹훅과 동기 응답이 동시에 도착 | 주문 상태 전이를 조건부 UPDATE(`WHERE status = 'pending'`)로 처리해 한 번만 반영 |

- 대사 작업 기본안: 10분마다 `pending`/`unknown` 상태로 5분 이상 지난 주문을 조회. 하루 1회 전일 결제 전체를 토스 내역과 대조.

### 7.2 RLS·권한
- `profiles`를 뺀 결제 테이블(`billing_settings`, `plans`, `subscriptions`, `billing_methods`, `payment_orders`, `payment_attempts`, `subscription_consents`, `guardian_consents`)은 `anon`/`authenticated` 역할에 SELECT/INSERT/UPDATE/DELETE 정책을 두지 않는다(=전부 거부).
- 프론트엔드에서 Supabase 클라이언트로 위 테이블을 직접 읽는 코드가 있으면 서버 API로 바꾼다.
- `profiles.plan`은 권한 판정에 쓰지 않는다. 판정은 `getEntitlement`만 한다. `profiles`의 본인 SELECT 정책으로 `customer_key`가 본인에게 보이는 것은 허용한다(빌링키가 아니며 카드 등록창 호출에 쓰는 값).

### 7.3 개인정보처리방침·이용약관 개정 (Q12 결정, 2026-10-28)

**결정:** 결제에 필요한 정보를 수집하도록 개인정보처리방침을 개정하고, **시행 7일 전**에 서비스 화면으로 고지한다(방침 제13조, `privacy.html:140`). 개정 방침이 시행되기 전에는 결제·보호자 동의 정보를 수집하지 않는다.

| 개정 항목 | 내용 |
|---|---|
| 수집 항목 추가 | 결제 기록(주문번호, 결제 금액·일시, 결제 상태, 카드사, 마스킹된 카드번호, 결제대행사 거래번호), 자동결제 고객 식별값(customerKey), 정기결제 동의 기록(동의 일시, 약관 버전, 고지 금액·주기, IP, 브라우저 정보), 연령 자기 신고(만 19세 이상/미만), 보호자 동의 기록(보호자 이름·관계·연락처, 동의 일시·결과, IP, 브라우저 정보) |

| 이용 목적 | 요금 결제·정기결제, 결제 분쟁 대응, 만 19세 미만 이용자의 법정대리인 동의 확인 |
| 처리 위탁 | 토스페이먼츠(결제 처리, 자동결제 빌링키 관리), 보호자 동의 메일 발송 업체(Q19 결정 후 기재) |

- L0 AUTH-4(수집 최소화)에 결제·보호자 동의 기록을 예외로 추가한다(L0와 같은 커밋).
- **이용약관은 두 번 개정한다.**
  1. **v1.1 (완료, 2026-10-29 시행):** 무료 체험 7일, 무료 운영 기간, 무료 이용 종료 후 안내. v1.0 가입자 경과 조치(30일 유지)를 부칙에 둬서 기존 이용자에게 불리한 변경이 없게 했다.
  2. **v1.2 (유료 조항):** 요금(월 13,900원), 정기결제, 해지, 청약철회·환불 기준(Q2), 만 19세 미만 법정대리인 동의 절차. 구독은 이용자가 직접 신청할 때만 성립하고 자동으로 청구되지 않으므로, 기본안은 **시행 7일 전 고지**다. 불리한 변경(30일 전)에 해당하는지 법률 검토를 받는다(Q21).

- 처리방침 제13조는 "이용자 권리에 중요한 변경은 30일 전"이라고도 정한다. 보호자 연락처 같은 새 항목 추가가 여기에 해당하는지도 함께 검토한다(Q21). 30일이 필요하다고 판단되면 고지일을 앞당기거나 시작일을 늦춘다.

공통 규칙
- 요청 본문의 `amount`, `planId` 이외의 가격 정보는 무시한다. 금액은 항상 서버가 계산한다.
- 결제를 만드는 모든 엔드포인트는 사용자별 잠금 + 진행 중 주문 재사용으로 중복 클릭을 막는다.
- `checkout/start`·`checkout/confirm`·`retry`는 연령 신고가 `minor_under_19`이면 같은 조건의 `approved` 보호자 동의가 있는지 서버에서 확인하고, 없으면 `403 guardian_consent_required`를 반환한다.
- 토큰 엔드포인트는 토큰 해시로만 조회하고, 시도 횟수 제한을 둔다. 응답에 보호자·학생의 전체 이메일을 넣지 않는다.
- §3.4 표의 AI 호출 라우트 7개에 `requireEntitlement` 미들웨어를 붙인다.
- 오류 응답은 기존 형식 `{ error: { code, message } }`을 따른다. 결제 관련 코드는 `ErrorCode`에 추가한다(`subscription_required` 등).
- 사용자별 잠금은 기존 `rate-limiter`처럼 메모리로 하지 않고 DB(부분 고유 인덱스, advisory lock)로 한다. 서버 인스턴스가 늘거나 재시작돼도 유지되어야 한다.
- 웹훅: 토스 결제 웹훅은 서명이 제공되지 않을 수 있다. 서명이나 IP 검증에 의존하지 않고, 받은 `orderId`/`paymentKey`로 결제 조회 API를 호출해 확인된 상태만 반영한다. 이 방식이면 위조 웹훅이 와도 상태가 바뀌지 않는다.
- 이 절의 엔드포인트는 `docs/API_SPEC.md`의 billing 절에도 같은 내용으로 적는다.

|---|---|
| 체험 → 유료 전환율 | 무료 이용 종료 후 14일 안에 첫 결제 성공한 사용자 비율 |
| 결제 시도 성공률 | 첫 결제·갱신 각각 승인/시도 |
| 구독 신청 이탈률 | 구독 신청 화면 진입 → 결제 성공까지 단계별 이탈 |
| 월 해지율 | 해지 예약 수 / 월초 활성 구독 수 |
| 중복 청구 건수 | 같은 `(subscription_id, period)`에 승인 2건 이상 — **목표 0** |
| 대사 불일치 건수 | 토스 내역과 DB 상태가 다른 건 — **목표 0** |
