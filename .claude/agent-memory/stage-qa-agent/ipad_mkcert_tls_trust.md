PocketQ's iPad LAN dev setup (`apps/web/vite.config.ts` / `apps/api/src/server.ts`) serves the frontend (`https://<LAN_IP>:5173`) and API (`https://<LAN_IP>:4000`) as two independent self-signed mkcert certs, no dev proxy between them (confirmed no `server.proxy` in `apps/web/vite.config.ts`). `docs/PROJECT_STATUS.md` §3.8's own incident log records the owner "manually dismissing" Safari's certificate warning only for the web origin (5173) to load the page at all — there is no record anywhere in `docs/PROJECT_STATUS.md` of the owner ever separately visiting `https://<LAN_IP>:4000` directly in Safari, nor of `mkcert -install`'s root CA (`$(mkcert -CAROOT)/rootCA.pem`, e.g. `/Users/soojin/Library/Application Support/mkcert/rootCA.pem`) ever having been transferred to and trusted as a profile on the iPad itself (Settings > General > VPN & Device Management > install, then Settings > General > About > Certificate Trust Settings > enable full trust).

**Why this matters**: iOS Safari's per-origin "visit this website" TLS trust exception does not extend to background `fetch()`/XHR calls to a *different origin* (different port counts as different origin). So even after fixing the mkcert cert's SAN to match the current LAN IP and correcting `VITE_API_BASE_URL`/`CORS_ORIGIN` in both `.env` files (a real, confirmed-necessary fix — see below), a `fetch()` from the web origin to the API origin on iPad can still fail at the TLS handshake layer with an opaque error, if the API origin's cert was never independently trusted on that device. curl with `-k` or a desktop browser with `mkcert -install` already run will show the pipeline as fully working (CORS preflight correct, 401 for missing auth, etc.) — that success does NOT prove the iPad will succeed, because desktop trust state and iPad trust state are independent.

**Compounding diagnosability gap (confirmed in code, 2026-09-05)**: `apps/web/src/features/problem-recognition/useRecognizeProblem.ts`'s `recognize()`/`resumeFromHistory()` catch blocks only special-case `error instanceof ApiError` (thrown solely by `parseApiErrorBody` in `apps/web/src/shared/api/recognizeProblem.ts`, which only runs when `fetch()` itself *resolved* with a non-ok HTTP response). Any raw `fetch()` rejection (TLS trust failure, CORS block, DNS failure, `AbortSignal.timeout` abort) is not an `ApiError`, falls into the generic `"문제 인식 중 오류가 발생했습니다."` branch, and — critically — is never `console.error`'d anywhere, so it's invisible even with Safari remote debugging unless you already know to check the Network tab. On top of that, `SolveLandscapePage.tsx`/`SolvePencilcanvasPage.tsx`'s failure `<Modal>` shows a fully hardcoded description ("사진이나 손글씨가 선명하게 보이는지 확인하고 다시 시도해 주세요.") regardless of the actual `recognizeErrorMessage` — so a TLS-trust failure, a CORS block, a 5MB `multer` payload-too-large (`apps/api/src/modules/recognition/upload.ts`'s `MAX_FILE_SIZE_BYTES`), a malformed-OpenAI-response 502, and a plain timeout are all **visually identical** to the user. This is why the same "문제를 인식하지 못했습니다" report recurred after the first (correct, necessary) IP/SAN fix — the popup carries zero information about which of several distinct causes is active.

**How to apply**: when this bug pattern recurs, don't stop at "env/cert now matches `ifconfig`". Ask/check next: (1) has the *API* origin (not just the web origin) ever been visited directly and trust-confirmed on the physical device itself, ideally via full mkcert root CA installation rather than per-origin click-through; (2) whether `useRecognizeProblem`/similar hooks log the raw caught error anywhere before mapping it to the generic message (they don't, as of 2026-09-05); (3) whether the failure modal's description reflects the actual error or a hardcoded string (hardcoded, as of 2026-09-05). Recommend (to the dev, not self-implemented — QA doesn't fix) adding raw-error logging and/or surfacing `recognizeErrorMessage` in the modal, and verifying actual `captureVideoFrame.ts` output Blob size on-device against the API's 5MB limit, as concrete low-risk diagnosability improvements. `mkcert`-based multi-origin real-device LAN dev is inherently a per-device, per-origin trust problem — env/cert-only fixes verified from a dev laptop are necessary but not sufficient evidence of an on-iPad fix; that final leg is unavoidably NOT VERIFIED — PHYSICAL DEVICE TEST REQUIRED until re-tested on the actual iPad.
