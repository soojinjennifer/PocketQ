**Verification technique — maskable safe-zone measurement without a physical device**: Python/Pillow bounding-box scan works well here since there's no device-only rendering nuance for a static PNG (unlike CSS/DOM layout). Load the image, sample a corner pixel as background, scan for pixels whose color distance from that background exceeds a small threshold (~12) to get the content bbox, then compute the distance from image center to each bbox corner and confirm all four are inside the claimed safe-zone radius. Confirmed here: max corner radius ≈198.3px inside a claimed 205px safe zone (512px canvas), background `#fbfaf6` matched exactly. Also confirmed the non-maskable icons (192/512/apple-touch-180) use near-full-bleed content (~80-90% of canvas) — meaningfully different from the maskable icon's tightly-cropped ~51%×58% content — proving the maskable-specific crop treatment was actually applied and not just copy-pasted across all 4 files.

Scope of this later round (confirmed via file mtimes, all in the 12:16–12:29 window, distinct from the morning round above): `RecognizedChip.tsx`/`.test.tsx`, `RecognizedProblemPopup.tsx`/`.test.tsx`, `SolvePencilcanvasPage.tsx`/`.test.tsx` only. **New HIGH bug found (not part of what was asked, but load-bearing for the same button): the "인식 취소" cancel-pill's `px-0 py-0` override never actually applies.** `Button.tsx`'s `pill-dark` variant's `PILL_BASE_STYLE` already sets `px-[26px] py-[11px]`; `RecognizedChip.tsx` passes `className="... px-0 py-0 ..."` intending to zero that out for the fixed 88×30 box. This *looks* like it should work (className is appended last in the JSX string), but **Tailwind v4's generated CSS output order is canonical (grouped/sorted by utility category and value), not based on the order classes appear in the `className` string** — `.px-0{padding-inline:0}` is emitted *before* `.px-\[26px\]{padding-inline:26px}` in the built `dist/assets/index-*.css` regardless of DOM class order, so with equal specificity the later-in-stylesheet `px-[26px]`/`py-[11px]` wins. Confirmed two ways: (1) grepping char offsets of the two selectors in the actual `pnpm build` output, and (2) rendering the exact `combinedClassName` string Button.tsx would produce in headless Chrome (`Google Chrome.app` binary, no Playwright installed) against the real built CSS and reading `getComputedStyle` — measured `paddingLeft/Right: 26px`, `paddingTop/Bottom: 11px` (not 0), causing "인식 취소" to wrap onto two lines and visually overflow above/below the intended 30px pill (screenshot confirmed) even though `getBoundingClientRect()` still correctly reports 88×30 (unaffected, since nothing conflicts with the explicit `w-[88px] h-[30px]`, and box-sizing:border-box keeps the outer box size independent of padding overflow). So the hitbox/touch-target math stays correct, but the button's actual visible rendering is broken — a real regression, not just a doc inaccuracy, and jsdom-based tests structurally cannot catch it (no real CSS cascade in jsdom); `RecognizedChip.test.tsx` only asserts class-name presence, not computed style.

**Reusable technique**: to verify any future "does this later className actually override this component's own base classes" claim, don't trust class-order intuition — build (`pnpm build`), grep the two candidate selectors' byte offsets in the emitted `dist/assets/index-*.css` (later offset = wins, assuming equal specificity/no `@layer` boundary between them), and/or render the exact combined class string in headless Chrome (`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome --headless --disable-gpu --dump-dom`, inject a `<script>` that writes `getComputedStyle(el)`/`getBoundingClientRect()` JSON into a `<pre>` for `--dump-dom` to capture, or `--screenshot` for a visual check) against the real built CSS — no Playwright/puppeteer dependency needed, system Chrome is sufficient.
**Why:** this project's `Button.tsx` `combinedClassName = base + variant + className` pattern (base sets `px-[26px] py-[11px]` for all pill variants) is reused everywhere; any future consumer trying to zero out that padding via a plain override class is likely to hit the exact same landmine.

**Re-verification round (2026-09-18, same day) of the `!px-0 !py-0` fix: STAGE PASS.** Development-agent changed exactly one className string (`px-0 py-0` → `!px-0 !py-0`) plus one new regression test; re-verified independently rather than trusting their report:

- Grepped the actual `pnpm --filter web build` output CSS directly for `.\!px-0{padding-inline:0!important}` / `.\!py-0{padding-block:0!important}` — present, `!important` makes cascade-order irrelevant (this is the correct fix, superior to reordering classes which would be fragile against future Tailwind version changes).
- Rebuilt the headless-Chrome repro from the prior round's technique **with a control**: same exact `combinedClassName` string rendered against the real built CSS both with `!px-0 !py-0` (single line, `Range.getClientRects()` top 5/height 19, fully inside the 88×30 box) and with `px-0 py-0` reverted back (2 separate text rects at top 2 and top 22, overflowing past the 30px box to bottom 41) — having a live before/after control in the same test harness is a stronger proof than testing only the fixed state, since it positively confirms the specific mechanism (not just "looks fine now").
- One measurement nuance worth remembering: `el.scrollHeight` (37) exceeding `clientHeight` (30) on this button is **not** a sign of leftover text overflow — it's the intentional `::before` hit-slop (`before:-inset-y-[7px]`, 30+7+7=44) counted as scrollable content of the `position:relative` parent. Don't mistake an absolutely-positioned hit-slop pseudo-element's contribution to `scrollHeight` for a layout bug; check `Range.getClientRects()` on the actual text content instead.
- Non-vacuous regression test check: reverted the one-line fix in the actual source file, ran `npx vitest run` on `RecognizedChip.test.tsx` for real (not just reasoning about it) — exactly the new test failed, the other 15 passed — then restored and confirmed `git diff --stat` matched pre-revert exactly.
- Root gate (`pnpm typecheck && pnpm lint && pnpm test && pnpm build`) all green: api 330/330, web 537/537 (canvas jsdom warning is the known non-failure noise, see [[test_commands]]).
- Chevron hitbox classes (`before:-left-[8px] before:-right-[19px] before:-inset-y-[13px]`, `size-[18px]`) and the cancel button's own layout classes (`h-[30px] w-[88px] shrink-0`, `before:-inset-y-[7px] before:inset-x-0`) were untouched by this round's diff — confirmed via `git diff` scoped to just this line, not a broader re-read.

**Why:** confirms `!important` (Tailwind v4 `!` modifier) is the durable fix for "later className must beat a component's own base utility classes" in this codebase's `Button.tsx` pattern, and that a before/after control pair in the same headless-Chrome harness is worth the extra 2 minutes over a single-state check.
**How to apply:** reuse the before/after control-pair technique for any future Tailwind cascade-override QA in this project; remember the `scrollHeight` vs `::before` hit-slop nuance so it isn't mistaken for a new bug in future PenRail/RecognizedChip/similar hit-slop-pattern re-checks.
