New multi-stage initiative separate from the main app: `Prompt/12. Problem DB.md` defines Stage 1 (Reference+Curriculum infra) → Stage 2 (PDF Analyzer) → Stage 3 (Problem Family Builder) → Stage 4 (Problem Generator) → Stage 5 (QA Pipeline) → Stage 6 (Supabase Production Import). Each stage must independently pass `stage-qa-agent` before the next starts (orchestration doc explicitly forbids self-declared PASS).

**Stage 1 (2026-08-25, completed, STAGE PASS)** built pure data infrastructure, isolated from the running app:
- Migration: `supabase/migrations/20260825000000_problem_db_stage1.sql` — `reference_sources`/`curriculum_nodes`/`curriculum_prerequisites`, all `create table if not exists`, RLS enabled with **no policies** (service-role-only by design — verified `apps/api/src/infrastructure/supabase/client.ts` uses the service role key, so this is correct, not an oversight). - The curriculum module is **not wired into `app.ts`/`server.ts`/any route** — confirmed via grep, meaning it cannot regress the running API. This "not yet wired in" pattern is expected through at least Stage 3-4; re-verify at each stage that it stays isolated until a stage explicitly says otherwise.

**Verification commands specific to this pipeline** (run directly, don't trust dev-agent's reported numbers):
```
pnpm -F api run db:validate-curriculum   # DB-less, pure JSON validation — prints "Errors: N, Warnings: N, PASS/FAIL" and per-subject node counts
```
This requires no Supabase credentials (good — makes it runnable in stage-qa-agent's sandbox). `db:import-curriculum` DOES require `.env` with real Supabase creds and actually writes, so do not run it in QA — code-review the repository/CLI for idempotency instead (upsert on natural keys, no `delete`, no auto-promotion of usage_mode).

- **Real defect found (HIGH, not yet fixed) — the reported "12/12 = 100% approved, CSAT relevance all HIGH (CORE=0/MEDIUM=0/LOW=0/REJECT=0)" result is a scoring-model artifact, not genuine differentiated evidence.** Root-caused by writing a throwaway script (not committed) that called the real pipeline's pure functions directly on the actual Stage 2 pilot families + Gold Set:
  1. `examEvidenceMatching.ts`'s `structuralSimilarity = (representationMatch + nodeOverlapRatio)/2` is computed from the SAME curriculum-node overlap that `passesCurriculumOverlapGate` already required to be >0 — so once the hard gate passes, `structuralSimilarity` is *always* >0, which alone is enough to push `comboScore` above 0 and classify as `WEAK`, even when `skillOverlap` and `reasoningOverlap` are both exactly 0.00 (verified directly: 11 of 12 families' gold evidence was 100% WEAK matches with `skillOverlap=0.00`/`reasoningOverlap≈0.00`, i.e. zero genuine skill/reasoning agreement — the WEAK classification came entirely from the residual node-overlap term). Only 1 family (FAM-ALG-EXPLOG-009) had one genuine COMPOSITE match with real skill/reasoning overlap.
  2. `familyApprovalWorkflow.ts`'s `MEANINGFUL_EVIDENCE` gate treats `goldEvidenceCount >= 1` as an unconditional PASS regardless of match-type strength (a WEAK match counts the same as DIRECT) — confirmed by reading the code, not just the unit test (the unit test only exercises `goldEvidenceCount` as an opaque number, never a WEAK-vs-DIRECT distinction).
  3. `csatRelevanceScoring.ts`'s `curriculumCentrality` dimension (25% base / 31.25% redistributed weight) is populated by the CLI as a hardcoded `curriculumNodesValid ? 1 : 0` (`calibrate-problem-families.ts`) — i.e. "are these codes real" — NOT the graph-centrality-via-`csat_importance` measure the module's own docstring says it should be. Since curriculum nodes are valid for virtually every family, this dimension is maxed at 1 for all 12 families unconditionally.
  4. The `reasoning` dimension (10%/12.5%) is populated with Stage 2's `family.confidence` (an extraction/segmentation-quality confidence, ~0.85 for most pilot families) — not a "reasoning reusability across other curriculum nodes" measure as the spec (`Prompt/12. Problem DB.md` §7.D) describes.
  - Net effect: curriculum(1.0) + reasoning(~0.85) alone contribute ~0.42 baseline score regardless of any real Gold evidence; adding just one spurious WEAK gold match (skillOverlap=0) pushes every single-item family to ~0.60-0.74, comfortably inside the HIGH band (≥0.55) and just under CORE (≥0.75) — which exactly explains the observed clustering and the empty CORE/MEDIUM/LOW/REJECT buckets. This is a genuine architecture/scoring-model defect (route to `plan-agent` first per the orchestration doc's defect-loop taxonomy), not a simple implementation bug — fix requires either tightening `MEANINGFUL_EVIDENCE`/`CSAT_USEFULNESS` to require match-type strength (not just count), decoupling `structuralSimilarity` from the same signal as the hard gate, and/or computing `curriculumCentrality`/reasoning-reusability from real signals instead of these placeholder proxies.
  - Minor related nit (LOW): `historicalCompatibilityGuard.ts`'s `selectCompatibleExamItems` is described in its own docstring as "the single point" for INCOMPATIBLE filtering, but `calibrateProblemFamilies.core.ts` reimplements the identical filter inline instead of importing it (only `validate-exam-features.ts`, a separate reporting CLI, actually calls the real helper). Both are logically equivalent and tested, but this is duplicated validation logic contrary to the module's own stated design.
