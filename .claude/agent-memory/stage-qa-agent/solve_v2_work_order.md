**Reproduction technique pitfall worth remembering**: my first attempt at reproducing the exact MEDIUM scenario (reach RESULT via `giveUp()`/solve → manually `router.navigate("/solve/pencilcanvas")` to simulate "browser back" → click "새 문제 풀기") produced a false alarm — the app appeared to redirect to `/camera` after the click, looking like a *new* regression. **HIGH finding discovered via own throwaway E2E test, NOT caught by any existing test (including the original 1차 stage-qa PASS) — "새 문제 풀기" (New Problem) button on `/solve/landscape`'s RESULT stage navigates to `/camera` instead of the intended `/solve/pencilcanvas`, for BOTH the solve-result and diagnosis-result paths.** Root cause: `SolveLandscapePage.tsx`'s `onNewProblem={() => { startNewProblem(); navigate("/solve/pencilcanvas"); }}` calls `startNewProblem()` first, which synchronously resets `problemId`/`recognizeStatus`/`capturedImage`/`strokes` etc. React 18 batches these into one re-render, but react-router's `navigate()` (even for a loader-less path change on a data router) resolves asynchronously — so React commits a render where `RequireProblemInputGuard` (still mounted, wrapping `/solve/landscape`) sees `isAllowed === false` (since `hasProblemInput`/`problemId` are now cleared) and its own `useEffect` fires `navigate("/camera", { replace: true })`. This second, later-queued navigation appears to consistently win the race over the handler's original `navigate("/solve/pencilcanvas")`, both in `createMemoryRouter` tests and (since the mechanism is React/react-router state timing, not a jsdom artifact) very likely in a real browser too. Confirmed reproducible on the plain solve-result (WORK-4 `giveUp()`) path with **zero diagnosis-related code involved** — i.e. this is a pre-existing regression in 1차's `onNewProblem` wiring (`SolveLandscapePage.tsx`), not something 2차 introduced, that simply had no full-app E2E coverage until now (the only prior tests were `ActionBar.test.tsx`'s isolated unit test with a mocked `onNewProblem`, and the 4b-정정-1차 fix's own repro test which exercised the *other* `onNewProblem` — the one in `SolvePencilcanvasPage.tsx`'s own ActionBar for the browser-back scenario, which is unguarded and thus never hits this race). **How to apply next time**: whenever a click handler calls both a state-resetting function AND `navigate()` in the same synchronous handler, and the *source* route is wrapped by a guard that redirects based on that same state, write a full-app E2E test (real `RouterProvider` + real guard, not an isolated component test) that asserts the *final* `router.state.location.pathname`, not just that some UI text appeared — an isolated `ActionBar.test.tsx`-style test with a mocked callback cannot catch a guard race, no matter how many assertions it has.

**Technique note**: reproduced by capturing the `router` instance returned from `createMemoryRouter` (return it alongside `render()`'s result from a local `renderApp` helper) and asserting `router.state.location.pathname` directly, plus `--reporter=verbose` was needed for `console.log` to actually print (default vitest reporter suppresses stdout for passing tests) — run via `npx vitest run --reporter=verbose <path>` from `apps/web/`, not the root `pnpm test` script (which doesn't forward `--reporter` cleanly through the recursive workspace runner and also runs the whole suite regardless of a path argument passed after `--`).
