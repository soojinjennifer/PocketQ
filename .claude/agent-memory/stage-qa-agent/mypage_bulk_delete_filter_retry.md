**Integrated stage QA verified 2026-09-09, STAGE CONDITIONAL PASS** for all 4 MyPage improvement items (thumbnail 72→120px, filter pill 1-line `flex-nowrap overflow-x-auto`, checkbox+bulk-delete via new `POST /api/problems/bulk-delete`, HistoryRow "다시 풀기" via new `ProblemInputProvider.resumeToWork()`). Backend security solid (auth required, `.eq("user_id", userId)` ownership scoping, 404 when nothing owned/deleted, error message never leaks Supabase internals — confirmed via `problems.router.test.ts`/`problemRepository.test.ts`). No delete path exists outside the confirm-modal's `onAction` (confirmed via grep — `bulkDeleteProblemHistory` has exactly one call site). `stopPropagation` on both new HistoryRow buttons (checkbox, "다시 풀기") is defensive-only — the outer row container is a plain `<div>` with no `onClick` of its own, so nothing would actually bubble even without it (documented in HistoryRow.tsx's own JSDoc, verified true by reading the file). Accessible names deliberately don't collide: HistoryRow's retry button uses `aria-label="다시 풀기 ${recognizedText}"` vs the HistoryDetailPanel/ResultPanel's plain "다시 풀기" button text — this exact ambiguity was a prior design-agent-caught bug, reconfirmed fixed.

**HIGH finding (confirmed via a throwaway repro test, not just code reading): `checkedProblemIds` (MyPage.tsx) is never reset or filtered when `selectedTag` changes.** Repro: select a tag filter → check an item → switch to a different tag filter that hides that item → the item stays checked (invisible) → "풀이 내역 지우기" is enabled and, when confirmed, actually deletes the invisible item too. The confirm `Modal` shows only generic text ("선택한 풀이 기록을 삭제하면 되돌릴 수 없어요"), never a count or list of what's about to be deleted — so a user has no way to notice they're about to delete items outside the current filter view. This is a real correctness/data-safety gap for a destructive, irreversible action (owner confirmed real server delete, not local hide) — not a crash/security issue, but exactly the kind of thing to flag HIGH under a destructive-action review.

**FIXED and independently re-verified 2026-09-09, STAGE PASS.** Fix scope confirmed via `git diff --stat` to be exactly 2 files (`MyPage.tsx`+`MyPage.test.tsx`, nothing else touched): (1) a `prevSelectedTag`-vs-`selectedTag` render-time-adjustment pattern (same "Adjusting state when a prop changes" idiom already used in `SolvePencilcanvasPage.tsx`'s `prevIsWorkStage`) resets `checkedProblemIds` to empty the instant `selectedTag` changes; (2) `handleConfirmDelete` additionally intersects `checkedProblemIds` with `visibleItems` right before calling the API, as defense-in-depth. Verified via 2 own throwaway repro tests (written, run, deleted) beyond the developer's own new committed test: (a) re-ran the exact original repro (narrow→check→widen→narrow-again→delete) — no leak; (b) a harder variant I devised myself (check items while filter is "전체"/all, THEN narrow to one tag) — also no leak, delete request contained only the currently-visible id. Full gate independently re-run (not trusting the self-report): typecheck/lint green, api 324/324 (unchanged), web 470/470 (469 baseline + 1 new test in `MyPage.test.tsx` naming the stage-qa finding directly), build green (same pre-existing >500kB chunk warning).
