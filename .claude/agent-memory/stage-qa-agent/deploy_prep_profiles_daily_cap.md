**STAGE PASS, verified 2026-09-09.** Two independent pieces bundled in one QA request: (1) `supabase/migrations/20260909000000_profiles.sql` (new, untracked, NOT applied — file-only per owner decision, owner applies manually at deploy time via dashboard SQL editor; no `supabase` CLI even installed in this env, confirmed no `db push` trace), (2) daily-10 soft usage cap on `POST /api/problems/recognize` (owner-confirmed: warn only, never block).

**Migration security review (code-review only, no live DB — migration not applied, so RLS behavior itself is NOT VERIFIED against a real Postgres, only the SQL text was reviewed):**
- `profiles` table: only a `profiles_select_own` SELECT policy (`auth.uid() = id`) exists; deliberately no INSERT/UPDATE/DELETE policy, so PostgREST/anon-key clients cannot write `plan`/`trial_ends_at` at all — writes can only happen via the trigger (`security definer`) or `apps/api`'s service-role client.
- Confirmed `apps/api` really does use the service-role key exclusively: `apps/api/src/infrastructure/supabase/client.ts` → `createClient(env.supabaseUrl, env.supabaseServiceRoleKey, ...)`, single cached client, same one `problemRepository.ts` imports via `getSupabaseServerClient()`. This is the precondition that makes "no INSERT/UPDATE/DELETE RLS policy" a valid design (server bypasses RLS by key, not by policy).
- Zero app code references the `profiles` table yet (`grep -rl "profiles" apps/api/src apps/web/src packages` → no hits) — confirms scope is genuinely schema-only, no hidden coupling.
- Design gap worth flagging to owner (not blocking, out of stated scope): `handle_new_user` trigger only fires on new `auth.users` INSERT, so **pre-existing users signed up before this migration runs will have no `profiles` row** — a backfill migration/script will be needed before any future gating logic reads `trial_ends_at` for existing accounts.

**Soft-cap "really soft" verification (traced by code, not just tests):**
- `apps/api/src/modules/recognition/recognition.router.ts`: `countProblemsCreatedToday` call is wrapped in its own try/catch *inside* the route handler (separate from the outer handler try/catch), and only attempted `if (userId !== "unknown")`. Any failure just leaves `dailyUsageCount`/`dailyUsageLimit` as `undefined` and falls through to `res.status(200).json(...)` — there is no code path where this feature can turn a successful recognize into a non-200 response.
- `problemRepository.countProblemsCreatedToday` itself is a "query method" (throws on Supabase error, unlike the best-effort `save*` methods) — this is intentional and safe *only because* the router wraps the call in its own local catch; don't mistake "throws" for "will break recognize" without checking the call site.
- Boundary math confirmed exact: `saveProblem` (which persists the just-created problem, `created_at = createdAt = now()`) is awaited *before* `countProblemsCreatedToday` runs, so the count includes the current request. Limit compare is strict `dailyUsageCount > dailyUsageLimit` (10), so the 10th call today shows no warning and the 11th (count=11) is the first to trigger — matches owner's "하루 10회" framing where the 11th call is the first over-limit one. (Caveat: if `saveProblem` itself silently failed — it's also best-effort/catches internally — that request wouldn't be counted, an inherent, acceptable limitation of a purely informational soft cap.)
- `getStartOfTodayUtcIso()` uses `Date.UTC(now.getUTCFullYear(), now.getUTCMonth(), now.getUTCDate())` — correctly timezone-independent (reads UTC getters, builds a UTC instant), and consistent with the rest of the codebase which already stores `created_at` via `new Date().toISOString()` (always UTC).
- Validation schema (`packages/validation/src/index.ts` `recognizeResponseSchema`): two new fields are `.optional()`. Confirmed this is safe for the *other* consumer of the same schema (`POST /api/problems/:problemId/reopen` in `apps/api/src/modules/problems/problems.router.ts`, and the frontend's `reopenProblemHistory`) — that response never sets the two fields, which is fine because they're optional; frontend explicitly zeroes them to `null` on reopen success (`useRecognizeProblem.ts`) so stale values from a prior recognize don't leak into the UI.

**Frontend modal (SolvePencilcanvasPage.tsx) nuance worth remembering:** the "오늘 문제풀이 횟수 안내" `Modal` is the same shared `fixed inset-0 z-50` backdrop component used by every other modal in the app (error dialogs, delete-confirm, etc.) — so while it's open it does visually/pointer-block the canvas underneath, same as any other modal in this codebase. "Does not block" in the owner's sense refers to *not gating the recognize/solve functionality or locking the user out* (recognize had already returned 200 before this modal even renders, and dismissing it is a single non-destructive click with no side effects) — it is NOT a claim that this is a non-modal toast. Don't flag the backdrop-blocking as a bug; it's consistent existing UX, not a regression.
- Minor cosmetic-only note (LOW, pre-existing pattern elsewhere too — see MyPage's delete-confirm `Modal` which also omits `icon`): this info modal passes no `icon` prop, so `Modal.tsx` falls through to rendering the default *email envelope* icon, which is semantically odd for a usage-count notice. Not introduced fresh by this stage (same omission pattern already exists in `MyPage.tsx`'s delete-confirm modal), so treat as a shared pre-existing Modal API gap (no explicit "info/neutral" icon variant exists) rather than a new bug in this stage.
- Dedup ref (`hasShownDailyUsageWarningRef`, shows the warning at most once per page mount) is correct by code reading (effect only sets state when the ref is still `false`) but has **no automated test exercising a second recognize call in the same mount** — the 4 existing tests each mount fresh with a single static context value. Coverage gap, not a functional bug (LOW).
